# CLAUDE.md

Wasat Shop — SPA интернет-магазина мужской одежды (React 19 + Vite 8 + Tailwind 4),
данные в Firebase (Auth через Google, Firestore с именованной базой, Cloud Functions, Hosting).
Интерфейс и тексты — на русском.

## Для кого и что важно

- Магазин сделан прежде всего для телефона: экраны проверяются на 390 px (и 320), раскладка для компьютера
  (от 1024 px) — отдельно, классами `lg:`.
- Владелец магазина — он же администратор: сам ведёт в админке каталог, склад, заказы и чат поддержки,
  а изменения смотрит по preview-ссылке в PR. Отчёты и описания PR он читает по-русски.
- Когда мелкое решение не описано ниже, решай его так, как решали во всех прошлых аудитах
  (`docs/ui-audit-plan.md`): покупатель не видит выдуманных данных; текст читается и нажимается на телефоне
  (WCAG AA); код админки не утяжеляет страницу покупателя.

## Как работать в долгих задачах

Если шаг не требует моего решения — продолжай. Статус пиши в том же сообщении, что и следующее действие.

Останавливайся и спрашивай, только если без меня дальше никак, или перед необратимым:
- слияние PR, push в `main`, `bun run deploy`, `firebase deploy` — это сразу публикует сайт и правила
  Firestore для покупателей (`.github/workflows/deploy.yml`);
- запись в боевую базу (проект `ai-studio-applet-webapp-e9574`): это данные магазина, из репозитория их
  не восстановить. Для проверок есть эмуляторы (README, «Локально с эмуляторами Firebase»);
- смена `ADMIN_EMAIL` или документов `admins/{uid}`: от них зависит, кто входит в панель администратора;
- изменения вне репозитория: Firebase Console, тариф, секреты и переменные GitHub.

Работа идёт в ветке от `main` и заканчивается pull request'ом; сливает его владелец. Название PR и коммитов —
по-русски, о том, что изменилось для покупателя или владельца (историю `main` читает он), без `feat:`/`fix:`;
большая работа — «Этап N из M: …». PR сливаются со squash, поэтому новый PR начинай от свежего `main`: если ветка
уже слита, пересоздай её (`git checkout -B <ветка> origin/main`), иначе в PR и в историю `main` попадут все её
прошлые коммиты.

Если задача больше нескольких шагов, веди список в `TASKS.md` (он в `.gitignore`, шаблон — `docs/templates/tasks.md`):
отмечай сделанное, дописывай найденное. Работа на несколько PR — план в `docs/` по шаблону
`docs/templates/audit-plan.md` (образец — `docs/ui-audit-plan.md`), новая функция — `docs/templates/feature-spec.md`.

Заканчивай каждый прогон тремя разделами: **Ждёт меня**, **Изменено**, **Найдено**. Описание PR — по шаблону
`.github/pull_request_template.md`: те же разделы («Ждёт владельца» вместо «Ждёт меня») и «Как проверить».

## Команды

- Менеджер пакетов — Bun (`bun install`, lock-файл `bun.lock`)
- `bun run lint` — `tsc --noEmit` (линтера ESLint нет); с `@types/react` проверяются и экраны: пропсы компонентов,
  `useState`, обработчики
- `bun run test:rules` — тесты `firestore.rules` в эмуляторе (нужна Java); сначала пишет образцы заказа `tests/.generated/`
- `bun run test:functions` — тесты Cloud Functions и расчёта цены (сначала `npm ci --prefix functions`)
- `functions/`: отдельный npm-пакет; `npm run typecheck|build --prefix functions`

## Когда готово

- Перед коммитом: `bun run lint && bun run build`; при изменении правил — `bun run test:rules`;
  при изменении `functions/` или `src/shared/` — `bun run test:functions`. Это те же проверки, что в CI.
- Изменение видно покупателю или в админке — проверено в браузере на эмуляторах (`VITE_USE_EMULATORS=true`)
  на 390 и 1280 px, а в разделе «Как проверить» описания PR сказано, что и на каком экране смотреть.
- Поменялось правило — обновлён `CLAUDE.md` или файл раздела в `.claude/rules/`, а при работе по плану — и план в `docs/`.
- Открытые находки аудита записаны тестами с пометкой `todo` (`tests/audit-attacks.test.mjs`,
  `functions/test/audit-orders.test.ts`): они не делают CI красным. Закрыл находку — сними `todo` у её теста, чтобы
  дыра не вернулась.

## Устройство

- Всё состояние — в `src/App.tsx`, экраны в `src/views/`, панель администратора
  в `src/components/admin/` (открывается из `ProfileScreen`).
- `src/shared/` — код, общий с Cloud Functions (расчёт цены `orderPricing.ts`, контракт
  `orderApi.ts`). Без браузерных API: этот код выполняется и на сервере. Меняя расчёт цены, меняете его и на сервере.
- Правила узких разделов — в `.claude/rules/`: этикетки и склад, аналитика, оферта и политика. Claude Code
  подгружает файл, когда открыт файл раздела; прежде чем планировать работу в таком разделе, прочитай его правила.
- История решений и замеры — `docs/ui-audit-plan.md`. Это журнал: ранние этапы описывают классы и палитру на свою
  дату (например, сиреневый акцент до этапа 5). Где журнал расходится с этим файлом, верен этот файл.

## Данные и доступ

- Работа с Firestore — только через `src/utils/firebaseSync.ts` (подписки `subscribeTo*`, запись `save*/sync*`):
  там запись частями под лимит батча, обработка ошибок и вырезание отзывов из товара.
- Клиент пишет в Firestore напрямую, поэтому безопасность = `firestore.rules`.
  Меняя поля документов или клиентские записи, обновляйте правила и
  `tests/firestore.rules.test.mjs`.
- Администратор: `ADMIN_EMAIL` в `src/context/AuthContext.tsx` (дублируется в `firestore.rules`)
  или документ `admins/{uid}`; отдельного пароля панели нет. Заказы и профили видны только владельцу
  и администратору. Гостевые заказы хранятся в `localStorage` и несут uid анонимного входа гостя: «Клиенты» группируют их
  как гостевые (по почте и телефону), если у этого uid нет профиля. Гость вошёл через Google — его заказы и переписка
  переходят в аккаунт (`handOverGuestData`, этап 7): обе стороны подтверждают связь (`guest_links/{гость}` пишет гость,
  `account_guests/{аккаунт}_{гость}` — аккаунт), потом гость меняет `customerUid` заказов и `threadId` своих сообщений
  (правила `isGuestOrderHandover`, `isGuestThreadHandover`), пакетами по 10; внутренние заметки остаются в старом диалоге.
- Себестоимость (`costPrice`) хранится только в `product_costs/{productId}` (читает и пишет администратор): товар
  читает любой посетитель. При записи товара поле вырезается (`toStoredProduct` в `firebaseSync.ts`, правило
  `keepsCostPriceOut`), админка получает товары с подмешанной себестоимостью (`adminProducts` в `App.tsx`), а старые
  значения из товаров переносит сессия администратора (`moveProductCostsToPrivate`).
- `users.bonusPoints/managerNotes/tags` меняет только администратор; заметки менеджера хранятся в `customer_notes`.
- Профиль покупатель пишет только своими полями разумного размера и с почтой своего Google-аккаунта (`isOwnProfileWrite`;
  новое поле профиля — добавить туда); при выходе профиль не пишется. «Клиенты» связывают карточку и заказы по `uid`.
  Имя отзыва и диалога не может выдавать себя за магазин (`isHonestName`). Чат администратора в `localStorage` не
  кэшируется; админка берёт последние 500 сообщений по `sentAt`.
- Резервная копия — «Витрина» → «Скачать копию базы» (`AdminBackupCard`, `exportDatabase` в `firebaseSync.ts`): JSON всех
  коллекций из `BACKUP_COLLECTIONS` (в том числе `promo_uses`) на устройство владельца, даты — `{ __timestamp }`. Новая коллекция — добавить
  в список и в `BACKUP_COLLECTION_TITLES` (`src/utils/backupRestore.ts`). «Восстановить из копии» (`AdminRestoreDialog`): режимы «Только
  недостающие» и «Как в копии», ничего не удаляет; отзывы, голоса и администраторов браузер не пишет (`RESTORE_SKIPPED`).
- ID базы Firestore — в `firebase-applet-config.json` (`firestoreDatabaseId`) и `firebase.json`.
- Ключи `manstyle_*` в `localStorage` и ID базы — внутренние, их не переименовывать: в ключах лежат корзина,
  избранное и гостевые заказы в браузерах покупателей (после переименования они пропадут), а ID базы связывает
  сайт с данными магазина.
- Демо-данных нет: пустая коллекция или поле = «не настроено» (компонент `NotConfigured`), ничего не засевается
  в Firestore и не подставляется покупателю; функциональная кнопка неактивна, пока нужные данные не заданы в админке.
  Причина: выдуманные контакты, реквизиты и профиль администратора увидел бы каждый покупатель, и они попали бы
  в счёт.
- Отзывы — коллекция `reviews/{productId}_{uid}` (меняет только автор), «Полезно» — `review_votes/{reviewId}_{uid}`.
  В `App.tsx` они подмешиваются в `product.reviews` (`mergeProductReviews`) и вырезаются при записи товара
  (`withoutCollectionReviews`). Внутрь товара отзывы не пишутся: товар меняет только администратор, а отзыв —
  только его автор (`firestore.rules`).
- CSV — только через `downloadCSV`/`csvCell` из `src/utils/csvHelpers.ts` (защита от формул Excel); импорт товаров
  не выдумывает значения и обновляет товар с тем же ID. Данные из базы в HTML-строках (отчет PDF) — экранировать,
  иначе текст из базы станет разметкой.

## Заказы и цены

- При `settings/server.serverOrdersEnabled == true` заказ оформляет функция `placeOrder`
  (`functions/src/placeOrder.ts`), иначе — клиент (`completeOrderLocally` в `App.tsx`: сначала дожидается записи
  заказа, потом списывает склад по строкам — `deductOrderLineStock` в `firebaseSync.ts`: транзакция на строку, в ней
  запись журнала и только `skus`, `inStock`, `lastStockMovement` товара). Режим серверных заказов включается
  в «Витрине» (`AdminServerOrdersCard`) только после ответа функции `placeOrder`.
- Пока заказы оформляет браузер, правила (`firestore.rules`) ограничивают покупателя (этап 1 аудита 02.10):
  - заказ — только поля, которые собирает `buildClientOrder` (`src/utils/clientOrder.ts`; `isClientOrderShape`: контакты
    и тексты разумной длины, до 30 строк, суммы в границах); строки поштучно не проверяются — не укладываются в лимит
    1000 выражений. Новое поле заказа из браузера — добавить в `isClientOrderShape`: тест правил пишет образцы
    `buildClientOrder` (`scripts/client-order-sample.ts`, все необязательные поля и заказ в 1 клик) и краснеет без этого;
  - списание (`isOrderStockDeduction`) — ровно один вариант строки сохранённого заказа, только остаток, только вниз
    и ровно на `changeQuantity` записи журнала `{заказ}_{строка}`, созданной в той же транзакции (поле товара
    `lastStockMovement`), — значит, один раз на строку. Части списка вариантов сравниваются срезами (`a[0:i] == b[0:i]`):
    так проверка не зависит от числа вариантов. `lower()` в правилах не меняет кириллицу — цвет строки и варианта
    должны совпадать буква в букву (с точностью до пробелов);
  - промокод — `usedCount` +1, не выше `usageLimit`, только вместе с отметкой `promo_uses/{заказ}` в одном пакете
    (`recordPromoUsageInFirestore`); выручку и комиссию браузер не пишет.

  - заказ — только под входом (Google или анонимный вход гостя из приложения `guest-chat`, как у чата) со своим
    `customerUid` и вместе с отметкой `order_rate/{uid}` в одном пакете (`placeClientOrder`): не чаще раза в 30 с с входа;
    `promo_uses` пишет только владелец заказа (этап 5 без Blaze).

  Поддельный заказ с анонимного входа по-прежнему списывает товар и может стоить 1 ₽ — это закрывают серверные
  заказы (тест A11 и A5 с `todo`). Без них: «Цены не совпадают с каталогом» в «Заказах» и на чеке (`orderPriceIssues`),
  «Оплачен» при расхождении — через подтверждение; автоотмена неоплаченных через `unpaidOrderCancelDays` из «Витрины»
  (`overdueUnpaidOrders`, срабатывает в «Заказах» у администратора). App Check включается ключом сборки
  `VITE_RECAPTCHA_SITE_KEY` (переменная GitHub `RECAPTCHA_SITE_KEY`), без ключа выключен. Фото строки заказа экраны берут только из каталога (`orderLineImage`): ссылку
  из заказа пишет посетитель, и чужая картинка выдала бы IP сотрудника.
- Суммы — только `src/shared/orderPricing.ts` (`toPricingLine`, `calcPromoDiscount`, `calcOrderTotals`) и в корзине,
  и в оформлении.
- Статус оплаты нового заказа — «Ожидает оплаты» или «Оплата при вручении» (`initialPaymentStatus` в
  `src/shared/orderApi.ts`, клиент и `placeOrder`); «Оплачен» ставит только администратор в «Заказах»: сайт денег не
  принимает, и правило `orders` не пускает `paid` от клиента. «Оплаченные» в аналитике — только подтверждённые. «Выручка», средний чек и «Сумма покупок»
  в «Клиентах» — только оплаченные заказы (`orderRevenue`, `isRevenueOrder` в `analyticsEngine.ts`; находка 29),
  «Постоянный покупатель» — от двух оплаченных.
- Реквизиты оплаты и чек («Доработки 5», `src/utils/paymentDetails.ts`):
  - шаблоны — коллекция `payment_templates` (читает и пишет только администратор; «Оплата» → «Шаблоны реквизитов»), три
    типа: СБП, карта, расчётный счёт; поля и проверки — `REQUISITE_FIELDS`/`validateRequisites` (р/с и к/с 20 цифр, БИК
    и КПП 9, ИНН 10 или 12, КПП обязателен при ИНН из 10 цифр);
  - к заказу реквизиты применяет администратор («Реквизиты оплаты» в карточке, `paymentDetails`), правка под заказ шаблон
    не меняет; покупатель видит только заполненные способы (`filledPaymentKinds`), номера копируются одними цифрами;
  - «Оплачено» → фото чека (JPG/PNG до 15 МБ, сжимается в браузере, PDF не принимается — без Blaze нет Storage) →
    сообщение в чат с `receiptOrderId` → заказ «Чек на проверке» (`receipt_review`, `paymentReceipt`, `paymentLog`;
    правило `isCustomerReceiptSubmit` сверяет сообщение покупателя). Только вошедший покупатель, гостю — реквизиты в чате;
  - «Подтвердить оплату» / «Отклонить чек» с причиной — в карточке заказа и на фото чека в чате (`reviewedOrder`), ответ
    магазина уходит в чат, покупателю — уведомление, пока сайт открыт. Чек на проверке — пульсирующая точка в статусе
    оплаты, бейдж в чате и в счётчике «Заказов».
- В строке заказа — облегчённая копия товара (`toOrderLineProduct` в `src/shared/orderLine.ts`, клиент, `placeOrder`
  и «Корректировка заказа»): без фото внутри документа, остатков, текстов карточки и себестоимости — иначе заказ
  из 2 строк товара с фото не помещался в 1 МиБ. Фото на экранах заказа — из каталога (`orderLineImage`). Заказ
  хранит `deliveryFee`, `discountAmount`, `promoCode` и из браузера, как из `placeOrder`.
- Заказ в 1 клик — без промокода и доставки (как в `placeOrder`) и убирает из корзины только заказанные строки.
- `usedCount` промокода растёт только при заказе (`recordPromoUsageInFirestore`, `increment` + `promo_uses/{заказ}`),
  не при применении.
- Комиссия партнёра — только для статистики (сайт её не выплачивает, решение владельца 02.10): считается из заказов
  с кодом, которые оплачены и получены клиентом (`paymentStatus == 'paid'` и `status == 'delivered'`), от суммы без
  доставки, по проценту из настроек кода (`computePartnerCommissions` в `src/utils/partnerCommission.ts`; «Промокоды» →
  «Реферальная система», «Аналитика»). Счётчики `commissionEarned`/`generatedRevenue` в промокоде может накрутить
  посторонний — на экранах их не показывать.
- Промокод (`src/shared/orderPricing.ts`, клиент и `placeOrder`):
  - срок `expiresAt` — «YYYY-MM-DD» из поля-даты, последний день включительно по Москве (`promoExpiryTime`);
    старые текстовые сроки («31 августа 2026 г.») читает `promoExpiryDate`;
  - ниже `minOrderAmount` скидка 0 в `calcPromoDiscount`, а применённый код перепроверяется при каждом изменении корзины
    и кодов и снимается с тостом-причиной (`App.tsx`);
  - покупателю в «Промокодах» — только `isPromoListed`: партнёрские, одноразовые из рассылки и из чата не показываются,
    если администратор не включил «Показывать покупателям» (`isPublic`). Сами документы `promos` пока читаются всеми
    (находка 10, закроется проверкой кода на сервере).
- Цена доставки — только у способа в «Доставка и ПВЗ» (`getAvailableDeliveryMethods`); бесплатно от порога способа, а без
  него — от порога «Витрины»; нет порога нигде — бесплатной доставки от суммы нет (5 000 ₽ по умолчанию больше не
  подставляются). Срок возврата и порог без значения в «Витрине» покупателю не показываются: плитки на главной, строки в
  карточке товара, полоса «до бесплатной доставки» в корзине, вопросы FAQ с `{FREE_DELIVERY}`/`{RETURN_DAYS}`.
  `courierDeliveryPrice`/`pickupDeliveryPrice`/`postDeliveryPrice` устарели и не читаются.
- Статус отменённого заказа в админке снова списывает товар со склада (`changeOrdersStatus`); если товара уже не хватает,
  сначала окно со списком недостающего (`stockShortages` в `src/utils/inventory.ts`).
- Отмена заказа (`src/utils/orderCancel.ts`, окно `CancelOrderDialog` — с причиной из списка и комментарием):
  - покупатель отменяет свой заказ (вход через Google) в профиле, под «Повторить заказ», только в «Принят» и один раз
    (`canCustomerCancel`; правило `isCustomerOrderCancel` пускает только поля отмены). Гость и заказ после начала сборки —
    через чат (`customerCancelHint`);
  - товар возвращается по строкам транзакцией (`returnOrderLineStock` в `firebaseSync.ts`): ровно столько, сколько
    списала запись журнала `{заказ}_{строка}`, вместе с записью `{заказ}_{строка}_return` (одна на строку, правила
    `isOrderStockReturn`/`isOrderStockReturnMovement`). Не вернулось (связь, заказ старше журнала) — `stockReturned:
    false`, браузер покупателя повторяет при следующем входе, а «Заказы» показывают «Вернуть на склад»;
  - администратор отменяет через «Ещё» → «Отменить и вернуть на склад» и массово — всегда с причиной (`CancelOrderDialog`,
    `cancelledBy: 'admin'`); товар возвращается тем же `returnCancelledOrderStock` по журналу (у заказа, восстановленного
    после отмены, — по заказанному, как его списал восстановленный). «Удалить заказ» у активного — сначала отмена
    с возвратом, затем окно «удалить навсегда или в архив»; у отменённого обе кнопки и в карточке (решение владельца 03.10).
    «Возврат средств» — только у оплаченного. Отменённый заказ через 3 дня уходит в чип «Архив» (`isArchivedOrder`,
    `archived` — вручную);
  - склад не включает «В продаже» у снятого с витрины товара (`isHiddenFromSale` в `applyStockChangeWithLogs`
    и `updateProductSkuStock`), распроданный после возврата снова в продаже.
- Статусы заказа по способу доставки («Доработки 4», `src/shared/orderFlow.ts` и `src/utils/orderFlow.ts`): тип заказа
  `deliveryKind` (`carrier` — Почта и ТК, `courier`, `pickup`; старые — по названию способа, `orderDeliveryKind`), цепочки
  `FLOW_STATUSES`, подписи — только `adminStatusLabel`/`customerStatusLabel` (не `ORDER_STATUS_LABELS`). Заказ перевозчика
  передаётся только с трек-номером (`statusChangeBlocker`), «Получен» ставит покупатель («Я получил заказ», правило
  `isCustomerReceiptConfirm`) или администратор вручную; курьер и самовывоз выдаются по коду (`pickupCode`, «Забрать
  заказ», только оплаченный или «Оплата при получении»; в окне выдачи — «Новый код», старый перестаёт действовать). Массовая
  смена статуса идёт по тем же цепочкам: заказ без такого шага, перевозчик без трека и выдача курьера/самовывоза (только
  по коду) пропускаются с названием, «Получен» — после «Закрыть заказы вручную?». Каждая смена статуса — запись `statusLog` (ISO-время, кто,
  `byUid` администратора, заметка); история заказа на экранах — `OrderTimeline`; смена статуса `historySteps` больше не дописывает (их читают только старые
  заказы и заявка на возврат из чата).
- «Корректировка заказа»: итог — товары + доставка заказа − его скидка (`adjustedOrderTotals`,
  `src/utils/orderAdjustment.ts`); процентная скидка — доля самого заказа, а не сегодняшний процент кода. Без изменения
  состава сумма и история не меняются. У отменённого заказа правки состава нет (товар уже вернулся), добавление без
  остатка — после окна со списком недостающего. Сайт денег не принимает: тексты о возврате и доплате — подсказка
  владельцу, а не обещание автоматики.
- Остатки меняются операцией, матрицей и инвентаризацией «Склада и SKU», формой товара или заказом; пакетного
  «пополнить всё» (+5/+10) нет. Форма товара сохраняет только остатки, изменённые в ней, — остальные берёт из базы на
  момент сохранения (`mergeFormStock`: иначе проданное за время открытой формы возвращалось), изменённые пишет в журнал.
  Склад по заказу из админки («Правка состава», восстановление и отмена восстановленного) меняется транзакцией на строку
  против остатка в базе (`applyAdminStockChanges` в `firebaseSync.ts`), а не записью товара из копии в браузере.
- Товар без вариантов (`skus`) — остаток 0, как в `placeOrder` (выдуманных «5 шт.» нет).
- Каждое изменение остатка — запись в журнале `stock_movements` («Склад и SKU» → «Журнал движений», общий код —
  `src/shared/stockMovements.ts`). Заказ пишет по записи на строку с id `{заказ}_{строка}` (клиент и `placeOrder` —
  в той же транзакции, что и списание) с фактическим количеством; автор записи заказа — всегда «Покупатель»
  (`ORDER_MOVEMENT_OPERATOR`), причина — «Заказ #…». Правила пускают покупателя только к записям своей строки
  сохранённого заказа; ненулевая запись — только вместе со списанием.
  Операции склада и форма товара пишут записи из админки (`saveStockMovements`), заказ из админки — в транзакции
  `applyAdminStockChanges`. Строки заказа без записи `{заказ}_{строка}` (у покупателя оборвалась связь) «Заказы»
  показывают как «Товар не списан со склада» с кнопкой «Списать со склада» (`findUntakenOrderLines`, заказы с
  `ORDER_JOURNAL_SINCE`).
- Предзаказ (`isPreorderMode`): распроданный вариант можно заказать (`getOrderableStock`), позиция получает
  `isPreorder` и не списывается/не возвращается на склад. Логика — и в `App.tsx`, и в `placeOrder`.
- Дата заказа — `createdAt` (ISO); `date` — только текст для показа (`formatOrderDate` из `src/shared/orderDate.ts`,
  клиент и `placeOrder`). Для расчетов — `orderTimestamp` (у старых заказов «Сегодня, 14:30» даты нет).

## Каталог, товар и корзина

- «Снят с витрины» — поле `product.hiddenFromSale` (переключатель формы товара и массовое действие, решение владельца
  02.10, находка 12), `product.inStock` — «есть в наличии». У старых товаров без поля `inStock == false` при ненулевом
  остатке = снят (`isHiddenFromSale` читает оба). Снятый товар не заказывается ни в клиенте (`getOrderableStock`, и как
  предзаказ), ни в `placeOrder`; возврат на склад снятому товару «В наличии» не включает. Фильтр каталога — один `matchesCatalogFilters`, без верхней границы цены
  по умолчанию (`DEFAULT_FILTER_STATE`); чипы цены — `buildPricePresets` по ценам каталога (пустых диапазонов нет).
- Пока каталог грузится — заготовки карточек (`CatalogLoadState`, `catalogStatus` из `App.tsx`), через 15 с —
  «дольше обычного… обновлять не нужно» без кнопки (перезагрузка начинала скачивание заново, находка 28), без сети —
  «Нет соединения», при ошибке подписки — «Не удалось загрузить каталог» с «Обновить страницу». «Не настроено» (каталог,
  категории) — только после ответа базы; пустой ответ из локального кэша (офлайн) ответом не считается
  (`subscribeToProducts`).
- Товаров сразу — 8 (`PRODUCTS_PAGE_SIZE` в `src/utils/productListing.ts`, решение владельца): «Популярное» на главной —
  8 и «Смотреть все», каталог — порциями по 8 с «Показать ещё»; новый поиск, фильтр или сортировка начинают с первой порции.
- Способы оплаты, FAQ и категории хранятся в `settings/storefront` (`paymentMethods`, `faqItems`, `categories`;
  вкладки «Оплата», «FAQ», «Категории», общий редактор `AdminListEditor`). Без способа оплаты оформление заблокировано.
- Разделы карточки товара (преимущества, состав, плотность, сертификаты, переплетение, посадка, страна, свои
  характеристики, уход) — поля товара из блока «Структура карточки» (`AdminProductCardStructure`); пустой раздел
  покупателю не показывается (`src/utils/productAttributes.ts`, без шаблонов по категории). Удаление элементов
  в форме товара — через `ConfirmDialog` с `preview` удаляемого, как в корзине.
  Отдельного поля «Материал» нет: `product.material` (фильтр материалов, поиск, накладные) заполняется из состава
  (`compositionToMaterial`). Плотность вводится числом, «г/м²» добавляет `formatFabricDensity`.
- Фото товара — `productImage(product, i)` (без фото — нейтральная заглушка, не сток); подписей ракурсов у фото нет
  (магазин их не задает) — только «Фото N из M». В товаре — лёгкие превью (`images`, ≈ 45 КБ), полные фото — документы
  `product_photos/{photoIds[i]}` (этап 6 без Storage, `src/utils/productPhotos.ts`): каталог качает только превью, страница
  товара, быстрый просмотр и увеличение — полные (`useProductPhotos`). Форма товара пишет фото раньше товара, удалённые —
  после; старые товары с фото внутри переносит сессия администратора (`moveProductPhotosOut`). Локального кэша Firestore
  нет: +22 КБ gzip к первой загрузке (замер 03.10) — вернуться при 100+ товарах. Рейтинг товара — только по реальным отзывам (`getProductRating`).
- Выбор варианта: размер заранее не выбирается, если размеров больше одного (`initialSize` из
  `src/utils/variantSelection.ts`), ни на странице товара, ни в быстром просмотре, ни в отзыве. Размер из «Подбора
  размера» хранится в профиле (`bodyMeasurements.preferredSize`, `russianSizeTop/Bottom`) и только помечается
  «Ваш размер» (`profileSizeFor`). «В корзину» без размера подсвечивает размеры. «+» на карточке при нескольких
  размерах или цветах открывает `VariantPickerSheet`. Добавление в корзину не уводит со страницы: тост с кнопкой
  «В корзину» (`addToast(text, type, action)`); обработчики добавления возвращают `false`, если ничего не добавлено
  (галочку «Добавлено» тогда не показывать).
- Корзина в браузере (`manstyle_cart`) — строки с облегчённой копией товара (`toStoredCart`/`loadStoredCart` в
  `src/utils/cartStorage.ts`, та же `toOrderLineProduct`, что в заказе): целые товары с фото занимали ≈ 0,5 МБ на строку,
  и после ≈ 9 строк корзина молча переставала сохраняться. Полный товар (фото, остатки) подставляет подписка на каталог.

## Оформление заказа

- Нижнее меню (`BottomNav`) на оформлении скрыто; контакты оформления — черновик в `sessionStorage`
  (`manstyle_checkout_contacts`). Подъезд и домофон обязательны только для курьера (`requireCourierDetails`).
- Оформление сверяет корзину с каталогом в базе (`orderStockProblems` в `src/utils/inventory.ts`): сверх остатка,
  снятое с продажи и удалённое — список «Не хватает на складе» над «Подтвердить» с фокусом и «Изменить корзину»; заказ
  не отправляется. `completeOrderLocally` проверяет то же (и для заказа в 1 клик).
- ФИО — три поля «Фамилия», «Имя», «Отчество» в профиле и оформлении (`src/shared/personName.ts`, решение владельца 02.10).
  Полное ФИО одной строкой (`fullName`) остаётся в `name` профиля и `customerName` заказа — его читают «Клиенты»,
  накладные, этикетки и чат; части — `lastName/firstName/middleName` профиля и `customerLastName/…` заказа. Старое имя
  одной строкой делит только для показа `namePartsOf`. Сохранённое ФИО не затирается именем Google-аккаунта
  (синхронизация профиля в `App.tsx`). Отчество обязательно для Почты и транспортных компаний (`requiresFullName`),
  галочка «Нет отчества» снимает требование. Части адреса (в том числе регион и комментарий курьеру) заказ хранит
  в `deliveryAddressParts` — для карточек с копированием в «Заказах» (`AdminOrderCopyCards`).
- Порядок оформления: контакты → способ доставки → адрес или пункт → оплата; шаг индикатора выполнен, только если
  выполнены предыдущие.
- Проверка — одна в `handleSubmit` (`noValidate`): ошибка у поля (`aria-invalid`, `aria-describedby`), фокус и
  прокрутка к первой, без тоста (тосты-ошибки не исчезают сами и копились бы).
- На телефоне внизу «Итого · Подтвердить», пока кнопка формы не на экране; на товаре — «цена · В корзину» над нижним
  меню.
- Город не подставляется (нет «Москвы» по умолчанию) и обязателен для курьера и почты; название перевозчика — из
  способа доставки, а не текстом в коде. Корзина показывает доставку по способам из «Доставка и ПВЗ»
  (`getAvailableDeliveryMethods`): одна цена — входит в «Итого», разные — диапазон и «Итого без доставки».

## Уведомления о заказе

- Сервера push нет: о смене статуса сайт сообщает, пока открыт (подписка на заказы в `App.tsx`) — звук, тост и системное
  уведомление. Системное — только с разрешения браузера и через service worker `public/notification-sw.js` (Android Chrome

  браузером; при запрете под ним — как разрешить.

## Чат поддержки

- Сообщения с `threadId` (uid покупателя; у гостя — анонимный uid из отдельного Firebase-приложения `guest-chat`).
  Чат из карточки заказа открывается с «Вопрос по заказу № …» в поле (`openSupportChat(orderId)` → `draftText`).
  У каждого сообщения есть поле `isInternalNote`: правила отдают покупателю только сообщения с
  `isInternalNote == false` и отклоняют запрос без этого фильтра, так что сообщение без поля он не увидит.
- Бота и автоответов нет: покупатель пишет только `sender: 'user'` (правила), отвечают сотрудники; приветствия нет —
  пустой диалог показывает «Диалог пуст», статус отправки — настоящий (`pendingChatIds`/`failedChatMessages`).
- У сообщения серверное `sentAt` (правила: `== request.time`); фото покупателя — только `data:image/…` (не внешняя
  ссылка). Покупатель правит/удаляет свое сообщение 15 минут (`canCustomerChangeMessage`, в правилах — по `sentAt`),
  сотрудники — любое без срока. «Удалить у себя» — `hiddenForCustomer`/`hiddenForStaff`, «у всех» — удаление
  документа (`applyChatMessageChange`).
- Фото чека к заказу — сообщение покупателя с `receiptOrderId` (правила пускают это поле, до 40 знаков); на нём
  администратор подтверждает оплату или отклоняет чек («Доработки 5»).
- Админка: один список диалогов `AdminSupportInbox` → `AdminSupportChatTab`; статус и приоритет диалога —
  `support_threads/{threadId}` (только администратор); статус для покупателя дублируется в
  `support_status/{threadId}` (читает сам покупатель, всплывающее уведомление при открытии чата). «Промокод» в чате:
  выбрать действующий из «Промокодов» (новый не создается) или создать новый.

## Админка

- «Запуск магазина» (`AdminLaunchChecklist`, шаги — `launchSteps` в `src/utils/launchChecklist.ts`): первой карточкой
  в «Аналитике», пока не заданы категории, товар, доставка, оплата или реквизиты; шаг открывает свой раздел.
  Шаблоны быстрых фраз в базу не засеваются — встроенные показываются, пока владелец не сохранит свои.
- Разделы — `AdminNav`: 4 группы (Продажи, Каталог, Маркетинг, Магазин), в группе 2–5 разделов. Раздел запоминается
  на сессию (`manstyle_admin_tab`). Счетчики «новых заказов» и «ждут ответа» считаются так же, как в чате:
  `summarizeSupportThreads`.
- Экраны и окна покупателя вне первого экрана (профиль, оформление, «Заказ оформлен», избранное, чат, «Промокоды»,
  реквизиты, быстрый просмотр, подбор размера, увеличение фото, заказ в 1 клик — последние четыре из
  `src/components/lazyWindows.ts`) — `lazy` через `src/customerLoaders.ts`, окна монтируются при первом открытии
  (`LazyMount`); после загрузки каталога они подгружаются в простое (`prefetchCustomerScreensWhenIdle`). Статический
  импорт вернёт их в главный бандл. Клиент Cloud Functions грузится только для серверного заказа (`placeOrderCallable`
  в `firebase.ts`), пакет `re2js` (регулярные выражения pipelines Firestore, магазину не нужны) заменён заглушкой
  `src/vendor/re2js-stub.ts` (`resolve.alias` в `vite.config.ts`). Главный чанк — 267 КБ gzip (этап 8, было 325).
- Админка — отдельный чанк: разделы и `AdminNav` в `ProfileScreen` подключены через `lazy`, id и типы разделов лежат
  в `adminSections.ts`. Компоненты админки (и `NeumorphicSelect`) не импортировать статически в код покупателя:
  Base UI и графики вернутся в главный бандл (раздельная загрузка сократила начальную с ~682 до ~386 КБ gzip).
  Библиотеки PDF (`html2canvas`, `jspdf`) тоже грузятся по требованию: в аналитике — `preloadPdfLibraries` при
  наведении, в этикетках — `import('jspdf')`; статический импорт вернул бы их в главный бандл. Скорость панели:
  - загрузчики разделов — `adminLoaders.ts` (только `import()`); администратору код панели подгружается заранее
    (`prefetchAllAdminWhenIdle` в простое, `prefetchAdmin` при наведении/нажатии на кнопку панели и на вкладки);
  - смена раздела — `startTransition`, один `Suspense` над разделами: текущий раздел остается на экране, пока грузится
    следующий (у вкладки — спиннер), «Загрузка раздела…» только при первом открытии;
  - график аналитики (recharts) — отдельный чанк `AdminAnalyticsChart`, карточки показываются без него;
  - тяжелые списки (заказы, клиенты) — `useProgressiveList`: первые карточки сразу, остальные после отрисовки.
- Несохраненное — `src/utils/unsavedChanges.ts`:
  - форма сообщает о правках через `useUnsavedChanges(dirty, 'Название')`;
  - `dirty` форм со снимком при открытии считает `useChangedSince(key, [поля])`;
  - при закрытии панели (×, клик по фону, Escape) и при смене раздела панель спрашивает «Закрыть/Перейти без
    сохранения?»; при уходе со страницы спрашивает браузер.

  Окно-форма закрывается через `useDiscardGuard` и `DiscardChangesDialog`, это касается и Escape. «Витрина»
  применяется кнопкой «Применить» (липкая панель при изменениях). Обновление из базы не затирает неприменённые правки.
- Сохранение: списки админки сохраняются через `syncAll*` (только запись, частями по 450 — лимит батча 500), в них
  передаются только изменённые элементы (`changedItems(prev, next)`: админка заменяет объект, а не мутирует его),
  удалённое убирает `deleteRemovedDocs`. Записи из админки в `App.tsx` — через `persist(label, ...writes)`: при ошибке
  тост «Не сохранено: …» и `false`; «Сохранено» показывать только после ответа базы (`AdminListEditor`, «Витрина»
  ждут `Promise<boolean>` от `onSave`/`onUpdateSettings`). Тосты-ошибки не исчезают сами. Записи покупателя, которые
  нельзя терять молча (профиль, очистка чата), — тоже через `persist`; счётчик промокода после заказа — в консоль
  с номером заказа (заказ уже оформлен).
- Строка списка: 2–3 частых действия на виду, редкие — в меню «Ещё» (`AdminActionMenu`, Base UI Menu, портал поверх
  панели), удаление — последним пунктом после черты и через подтверждение. «Заказы»: чипы статуса (`role="radio"`,
  отмененные — отдельным чипом) и «Фильтры (n)» (период, оплата, доставка и способ оплаты — названия из самих
  заказов, не из кода).
- На телефоне (< sm) панель администратора во весь экран; в чате поддержки карточка заказа свернута. Вход в панель —
  наверху профиля. Форма товара: «Отмена / Создать» закреплены внизу окна. Проверка формы товара — одна, на «Сохранить»:
  список ошибок над этими кнопками (`role="alert"`, дальше обновляется сам), без тостов; Enter в поле не отправляет
  форму, а в строке «добавить» (ссылка на фото, цвет, размер — `data-enter-adds`) нажимает её кнопку. Счётчик «Место под
  фото и описание» (`src/utils/productSize.ts`, запас до 1 МиБ) считает фото превью (полные — в `product_photos`), товар
  больше запаса не сохраняется. Форма закрывается и пишет «сохранен» только после ответа базы (`onUpdateProducts` →
  `Promise<boolean>`). Поля ввода текста в админке — `resize-y`,
  как в FAQ.

## Интерфейс

### Стили и цвета

- Стили — неоморфные классы из `src/index.css`, тени только через их переменные (`--neu-*`). Классы `neu-*` объявлены
  вне CSS-слоев и сильнее утилит Tailwind (`@layer utilities`): рядом с `neu-*` не работают `shadow-*`, `bg-*`
  (и `hover:bg-*`) и `active:scale-*` (у кнопок свое нажатие), поэтому их туда не добавлять; цветная подложка
  статуса — элемент без `neu-*` (`bg-danger-soft border ...`).
- Одна `neu-button-accent` на экран, удаление — `neu-button-danger` + `ConfirmDialog`. Выпуклое `neu-button` —
  только то, что нажимается; статичные плитки и чипы — `neu-flat`/`neu-flat-sm`.
- Невыбранный вариант выпуклый, выбранный вдавлен (`neu-pill-active`: тень и тонкая обводка accent внутри —
  `--neu-selected-rim`, второй признак кроме тени); `neu-inset` — лунки и поля, не варианты выбора. Неактивная
  (`disabled`) кнопка или вариант — плоская `neu-button-disabled`, не вдавленная (вдавлено = выбрано).
- Переключатель — `NeumorphicSwitch` (`role="switch"`, `aria-checked`, `aria-label`); галочка выбора в списках
  админки — `SelectCheckbox` (`role="checkbox"`); выбор одного варианта (доставка, оплата) — `role="radio"`
  в `role="radiogroup"`.
- Цвета статусов — только токены `success/warning/danger` (и `*-soft` для подложек), не emerald/rose/amber/sky/
  slate/gray: токены подобраны под контраст 4.5:1 и на фоне, и на подложке. Статус заказа — `orderStatusChip`
  (`src/utils/orderStatusStyle.ts`), одинаково во всех разделах.
- Цвета бренда — токены `@theme` в `index.css`: `accent` (тёмно-синий #2C4A6B: ссылки, выбранное, иконки;
  `text-accent`, `bg-accent/10`), `accent-strong` для наведения; главная кнопка и заливки — графит
  (`neu-button-accent`, `neu-fill-accent`); золото `gold` — только бейджи «Хит/Premium» (`photoBadgeClass`
  в `src/utils/productBadge.ts`). Хексы акцента в классах не писать: палитра бренда уже менялась, и меняется
  она в одном месте — `@theme`. Графики, карта и PDF — свои цвета.
- Заголовки h1–h3 и `font-display` — Manrope (`@fontsource/manrope`), текст — системный шрифт.

### Окна и выпадающие списки

- `.neu-modal` имеет `transform` и `contain: paint`: полноэкранное окно (`fixed inset-0`) внутри него обрезается.
  Окна поверх панели администратора и формы товара выводить через `ModalPortal` (как `ConfirmDialog`).
- У каждого окна — `useDialogA11y(open, onClose)` (`src/utils/useDialogA11y.ts`): `ref` и `props` на панель окна,
  `titleId` на заголовок (или `label`). Хук дает `role="dialog"`, фокус внутрь (`data-autofocus`), Tab внутри окна,
  Escape только верхнему окну и возврат фокуса. Свои обработчики Escape и `aria-modal` окнам не писать: второй
  обработчик закроет и окно под верхним.
- Вместо нативного `<select>` — `NeumorphicSelect` (Base UI Select, меню в портале поверх окон): пункт плоский,
  под курсором или стрелками выпуклый (`neu-option`), выбранный вдавлен; `groups` — заголовки групп, `layout="grid"` —
  плитки с иконкой (выбор иконки категории). Ключи `CATEGORY_ICONS` не переименовывать: ключ хранится в категории
  в базе, и с новым именем категория покажет иконку «другое». Вкладки админки — Base UI `Tabs` (`@base-ui/react`,
  только headless-логика, стили `neu-*`).

### Анимации

- Классы появления `animate-in fade-in zoom-in-95 slide-in-from-top-2 duration-*` определены в `index.css`
  (пакета tw-animate-css нет); анимация без `fill-mode: forwards`, чтобы у окна не оставался `transform`.
- «Уменьшить движение» в системе: `MotionConfig reducedMotion="user"` в `main.tsx` и `@media (prefers-reduced-motion)`
  в `index.css` (без появления, пульсаций и «лучей»; спиннеры крутятся). Бесконечную декоративную анимацию добавлять
  в этот список.
- Баннер на главной листается сам только без «уменьшить движение» и останавливается при наведении, фокусе, касании
  и кнопкой паузы; слайд открывается кнопкой-заголовком.

### Доступность

- Текст не мельче `text-[11px]`; абзацы (`<p>`) — от `text-xs`, 11 px только бейджи, подписи нижнего меню
  и надзаголовки капсом. Начертание не жирнее `font-extrabold`: Manrope загружен 700 и 800 (заголовки h1–h3 и `font-display` — только
  `font-bold`/`font-extrabold`; 600 убран ради скорости первого экрана), и `font-black` не сработает.
- Вторичный текст #4E5C70, акцентный текст — `text-accent`.
- `outline` не отключать: фокус — через `:focus-visible` в `index.css`, и у графиков Recharts тоже; на фото
  `neu-photo-btn` — темное кольцо внутри белого. Кнопке из одной иконки — `aria-label`.
- Распроданный, но доступный для выбора вариант — без прозрачности (зачеркнут, «нет»); прозрачность только у `disabled`.
- У поля — видимая подпись `<label htmlFor>` (или `aria-label`) и `autoComplete` для имени, телефона, почты, адреса.
- Кликабельное — `button`, не `div` с `onClick`; карточка товара открывается ссылкой-названием (`productHref`),
  растянутой на карточку (`after:absolute after:inset-0`). Зона нажатия не меньше 24 px, у частых действий
  покупателя — 32 px.

### Тексты и названия

- Название магазина не прописывать в текстах: оно задаётся в «Витрине» и уже менялось (MANSTYLE → Wasat Shop).
  Брать `getStoreName(settings)` / `currentStoreName()` из `src/utils/storeContacts.ts` (там же контакты без
  демо-значений). Номера заказов и новые артикулы — `WS-`.
- Склонения — только `pluralRu` (`src/utils/pluralize.ts`).

### Навигация

- Экран — в адресе (`#/catalog`, `#/product/{id}`, `src/utils/navigation.ts`). Экран меняется только через
  `setActiveTab` из `App.tsx` (обертка: запоминает прокрутку): новый экран — новая запись истории и открывается сверху,
  «Назад» браузера и в шапке (`handleHeaderBack`) возвращает на прошлый экран с его прокруткой; подтверждение заказа
  заменяет запись оформления. Ссылка на удаленный товар ведет в каталог с сообщением.
- Нижнее меню — иконки с подписями; товар подсвечивает «Каталог» (как `DesktopHeader`, где оформление подсвечивает «Корзину»).
- Боковое меню (`SidebarDrawer`) — только то, чего нет внизу и в шапке: фильтры, размеры, бренд и реквизиты,
  поддержка, документы; экраны магазина в нем не дублировать.

### Раскладка на компьютере

Брейкпоинт `lg` (от 1024 px), только классами `lg:`; телефон и планшет не меняются. На компьютере:
- оболочка `max-w-6xl`;
- вместо `BottomNav` (`lg:hidden`) — `DesktopHeader`: название, поиск, разделы со счетчиками, меню;
- «Назад» и заголовок экрана — `DesktopTitleRow` в `<main>`, чтобы ориентир banner был один;
- товар, корзина и оформление — две колонки, правая `sticky`;
- каталог — фильтр слева (`CatalogAdvancedFilter variant="sidebar"`, применяется сразу);
- админка — во весь экран, группы меню слева.

Оболочка и `<main>` — `overflow-x-clip`, не `hidden`: иначе `sticky` не работает. Поиск каталога один на шапку,
главную и каталог (`catalogSearch` в `App.tsx`).

## Деплой

GitHub Actions `deploy.yml`: push в `main` публикует Hosting и правила, PR получает preview-канал (живёт 3 дня).
Каналов у сайта ограниченное число, поэтому перед созданием preview workflow удаляет каналы закрытых и слитых PR
(`pr<N>-…`); каналы открытых PR остаются (не больше 8 самых новых, кроме своего) — владелец проверяет несколько PR
сразу. Боевой `live` не трогается. Нужен секрет `FIREBASE_SERVICE_ACCOUNT`. Перед публикацией в `main` — lint, тесты
правил и `test:functions` (цена, корзина, склад) всегда, не только при `DEPLOY_FUNCTIONS`; токен GitHub у проверок
и деплоя — только чтение (`permissions: contents: read`).
CLI публикует правила раньше сайта, поэтому правило, которое отклонит запись старого сайта (новое обязательное поле,
новый пакет записей), выпускается двумя PR: сначала сайт пишет новое (старые правила это пускают), потом правило
требует его. Иначе между публикацией правил и сайта, а также в открытых вкладках покупателей заказы не оформятся.
Preview работает с боевой базой (своего проекта для проверок нет), поэтому его сборка получает `VITE_PREVIEW_BUILD=true`
и показывает на каждом экране плашку «Проверочная версия… данные настоящие» (`PreviewBanner`, `IS_PREVIEW_BUILD`),
а в панели администратора — предупреждение под заголовком. В боевой сборке этого кода нет.
