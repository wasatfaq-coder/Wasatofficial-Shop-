# Поле, коллекция или правило Firestore

Браузер пишет в Firestore напрямую, поэтому граница безопасности — `firestore.rules`, а ошибка в правиле — это либо дыра
для любого посетителя, либо заказы, которые не оформляются. Скопируй чек-лист и отмечай:

```
- [ ] 1. Запись и подписка — в firebaseSync.ts
- [ ] 2. Правило: кто читает, кто пишет, какой формы документ
- [ ] 3. Тесты правила: кому можно и кому нельзя; test:rules зелёный
- [ ] 4. Старые документы без поля работают
- [ ] 5. Выпуск: одним PR или двумя
- [ ] 6. Резервная копия
- [ ] 7. Индекс каталога (если поле нужно каталогу)
```

**1. Код.** Запись и чтение — только функциями `src/utils/firebaseSync.ts` (`subscribeTo*`, `save*`/`sync*`): там пакеты
под лимит 500 записей, обработка ошибок и вырезание отзывов и себестоимости из товара.

**2. Правило.** Для каждой операции реши, кто её делает: посетитель, сам покупатель, администратор. В правиле —
владелец документа, список допустимых ключей, типы и размеры строк и списков: админка читает документы всех, и
огромный документ одного покупателя тормозит её у владельца. Готовые места:
- новое поле профиля покупателя — в список `isOwnProfileWrite`; поля `adminOnlyProfileFields` покупатель не пишет;
- поле заказа — `isClientOrderShape`, сначала прочитай `.claude/rules/orders.md`;
- имя, которое видят другие (отзыв, чат), — через `isHonestName`.

**3. Тесты** — в `tests/firestore.rules.test.mjs`, рядом с тестами той же коллекции: `assertSucceeds` для того, кому
можно, и `assertFails` для гостя, чужого покупателя и документа сверх размера. Петля:

```bash
bun run test:rules
```

Упало — исправь правило или тест по смыслу и запусти снова; дальше — только на зелёном. Тест, который «мешает», не
удалять и не ослаблять: он и есть граница. В облачной сессии команда работает: Java есть, эмулятор скачивается при
первом запуске.

**4. Старые документы.** В базе уже лежат документы без нового поля: чтение берёт значение по умолчанию, правило
проверяет поле, только если оно меняется (как `isOwnProfileWrite`). Боевые данные не переносить: запись в базу
`ai-studio-applet-webapp-e9574` — только владелец, проверки — в эмуляторах.

**5. Выпуск.** Публикация выкладывает правила раньше сайта, а у покупателей открыты вкладки со старым сайтом.
Правило, которое отклонит запись старого сайта (новое обязательное поле, новый пакет записей), выпускается двумя PR:
первый — сайт пишет новое, а старое правило это пропускает; второй, после публикации первого, — правило требует
новое. Ослабляющее или новое для новой коллекции правило — одним PR.

**6. Резервная копия.** Новая коллекция с данными владельца — в `BACKUP_COLLECTIONS` (`src/utils/firebaseSync.ts`)
и с русским названием в `BACKUP_COLLECTION_TITLES` (`src/utils/backupRestore.ts`); иначе «Скачать копию базы» её
молча пропустит. Временные и производные (`client_errors`, `catalog_index`, `product_thumbs`) — не добавлять.

**7. Индекс каталога.** Поле нужно списку, фильтру, сортировке или карточке каталога — добавь его в `CatalogEntry`
и подними `CATALOG_INDEX_FORMAT` на 1 (`src/utils/catalogIndex.ts`): сессия администратора перепишет индекс сама,
сценарии в браузере возьмут его из `catalogIndexDocs`.

Поменялось то, что покупатель читает при визите, — замер `bun run measure:visit` до и после (скилл
`doing-plan-stages`, шаг 4). PR — скилл `shipping-prs`; его скрипт сам запустит `test:rules` и сценарии.
