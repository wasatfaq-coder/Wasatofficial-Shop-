# PR от ветки до слияния

Слияние в `main` сразу публикует сайт и правила Firestore для покупателей (`.github/workflows/deploy.yml`), поэтому
PR сливается только зелёным и только со свежим `main`. Скопируй чек-лист в ответ и отмечай шаги:

```
- [ ] 1. Ветка от свежего main, чужого PR на ту же работу нет
- [ ] 2. Проверки прошли
- [ ] 3. Коммит и push
- [ ] 4. PR по шаблону
- [ ] 5. CI зелёный на последнем коммите
- [ ] 6. Свежий main в ветке, CI снова зелёный
- [ ] 7. Слит (если разрешено), публикация прошла
```

## 1. Ветка

`git fetch origin main`. Если PR этой ветки уже слит — `git checkout -B <ветка> origin/main`: PR сливаются со squash,
и без этого старые коммиты ветки снова попадут в PR и в историю `main`.

Открытые PR (`github:list_pull_requests`) смотри до начала: у владельца бывает параллельная сессия в том же
репозитории, и этапы уже делались дважды. Есть PR на ту же работу — не открывай второй и не пиши в чужую ветку, а скажи
владельцу.

## 2. Проверки

Запусти скрипт, не меняя флаги:

```bash
bash "${CLAUDE_SKILL_DIR}/checks.sh"
```

Он выбирает команды CI по изменённым относительно `origin/main` файлам (выбор — в заголовке скрипта) и
останавливается на первой упавшей. `--dry-run` только покажет выбор, `--all` запустит всё, как CI. Упало — исправь
и запусти снова; дальше — только после «Все нужные проверки прошли». В облачной сессии работают все проверки (замер
04.10: правила ≈ 1 мин, сценарии в браузере ≈ 4 мин), долгий запуск — в фоне.

Изменение видно покупателю или в админке — посмотри его на эмуляторах на 390 и 1280 px: скрипт этого не заменяет.

## 3. Коммит

Заголовок — по-русски, что изменилось для покупателя или владельца: историю `main` читает владелец. Без `feat:`/`fix:`;
этап плана — «Этап N из M: …». Примеры из истории `main`:

- «Отчёт об ошибке покупателя не теряется, когда в часе заняты несколько ячеек журнала»
- «Этап 5 из 6: картинки баннеров хранятся отдельно, главная читает только показанный слайд»

Плохо: «fix: client errors slot race». Строки авторства в конце коммита — из указаний сессии, если они там есть.

## 4. PR

`github:create_pull_request`, база `main`, заголовок — как у коммита. Описание — разделы
`.github/pull_request_template.md`: «Ждёт владельца» (нечего — «Ничего»), «Изменено», «Найдено», «Как проверить»
(какой экран открыть на preview, на телефоне или компьютере), «Чеклист» с настоящими отметками. Блок авторства —
первыми строками, если сессия его задаёт. Поменялось то, что покупатель читает из базы, — таблица `bun run measure:visit`
до и после.

После создания подпишись на события PR (`claude-code-remote:subscribe_pr_activity`), если инструмент есть: CI и
отзывы придут сами, опрашивать не нужно.

## 5. CI

Проверки PR: «Typecheck & build», «Firestore rules tests», «Cloud Functions tests», «Browser scenarios (390 & 1280 px)»
из `ci.yml` и «Preview channel (PR)» из `deploy.yml`. Состояние — `github:pull_request_read` с `get_check_runs`.

Красная — лог (`github:get_job_logs`), та же команда локально, причина, исправление, снова шаг 2. «Плавающий тест» —
не причина: прошлые случаи оказались гонкой с записью после экрана «Заказ оформлен» и зависшей анимацией, то есть
ошибками, которые увидел бы покупатель. Тест не отключать и не пропускать. Сценарии — скилл `writing-e2e-scenarios`.

## 6. Свежий main

На `main` правило: ветка PR должна быть не позади `main`, иначе слияние вернёт 405 «required status checks are
expected». Перед слиянием:

```bash
git fetch origin main && git merge origin/main
```

Слиянием, а не rebase: ветка уже опубликована. Конфликт в `bun.lock` — пересобери `bun install`, а не правь руками.
Потом шаг 2, push и снова зелёный CI на новом последнем коммите.

## 7. Слияние

Сливай, только если владелец разрешил: в этой задаче или постоянным решением («сливать зелёные» в памяти проекта).
Иначе остановись на зелёном PR и напиши владельцу, что PR ждёт его, — так требует `CLAUDE.md`, потому что слияние
публикует сайт.

`github:merge_pull_request` с `merge_method: squash` и `expectedHeadSha` — тем коммитом, у которого видел зелёный CI:
если кто-то запушил после проверки, слияние откажет, а не опубликует непроверенное. Готовых PR несколько — по одному:
каждое слияние отбрасывает остальные назад к шагу 6.

После слияния найди запуск «Deploy to Firebase» на коммите `main` (`github:actions_list`). Красный — сразу скажи
владельцу, какой шаг упал: при сбое публикации или шага «Сайт открывается после публикации» покупатели могут видеть
старый или сломанный сайт.

Готово — это PR слит и его публикация зелёная, или PR зелёный и ждёт решения владельца, и это сказано.
