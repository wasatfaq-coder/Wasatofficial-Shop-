## Админка

- «Запуск магазина» (`AdminLaunchChecklist`, шаги — `launchSteps` в `src/utils/launchChecklist.ts`): первой карточкой
  на «Сегодня», пока не заданы категории, товар, доставка, оплата или реквизиты; шаг открывает свой раздел.
  Шаблоны быстрых фраз в базу не засеваются — встроенные показываются, пока владелец не сохранит свои.
- Меню — `AdminNav`, вариант А (решение владельца 09.10, этап 2 `docs/admin-wholesale-plan.md`): на телефоне снизу
  «Сегодня, Заказы, Товары, Чат, Ещё», «Ещё» (раздел `more`) — остальные разделы списком по группам со строкой «для чего он»;
  на компьютере все разделы слева. Кнопки с `aria-current="page"`, не вкладки; сценарии e2e переходят через
  `openAdminSection`. Панель открывается на «Сегодня» (`AdminTodayTab`, расчёт — `src/utils/adminToday.ts`): что ждёт
  (заказы, чеки, чат, мало на складе), плашка «Курс не обновлялся N дней», выручка за 7 дней — только оплаченные. Раздел
  запоминается на сессию (`manstyle_admin_tab`). Счетчики «новых заказов» и «ждут ответа» считаются так же, как в чате:
  `summarizeSupportThreads`. Меню строки называет строку («Ещё: заказ № …», проп `of` у `AdminActionMenu`).
- «Витрина» (`AdminStorefrontTab` + `src/components/admin/storefront/`) — Base UI Tabs: «Приём заказов» (первый), «Контакты и график»,
  «Реквизиты», «Тексты о бренде», «Резервная копия» (сохраняется сразу). Одна «Применить» (липкая панель) шлёт
  `{ ...сохранённая версия, ...поля STOREFRONT_FORM_FIELDS }` (`storefrontForm.ts`); несохранённое сравнивается и обновление из базы
  сливается (`mergeIncoming`) только по этим полям. `settings/storefront` пишется изменёнными полями —
  `saveStorefrontSettingsToFirestore(settings, before)` (`setDoc` с `mergeFields`, `deleteField` для убранных): раздел пишет только свои поля.
  Порог бесплатной доставки и «Экспресс-доставка» — только в «Доставка и ПВЗ» → «Для всех способов» (`DeliveryCommonSettings`);
  выключенная экспресс-доставка прячет способы с id `express` и с типом `express` (`getAvailableDeliveryMethods`).
- Экраны и окна покупателя вне первого экрана (профиль, оформление, «Заказ оформлен», избранное, чат, «Промокоды»,
  реквизиты, быстрый просмотр, подбор размера, увеличение фото, заказ в 1 клик — последние четыре из
  `src/components/lazyWindows.ts`) — `lazy` через `src/customerLoaders.ts`, окна монтируются при первом открытии
  (`LazyMount`); после загрузки каталога они подгружаются в простое (`prefetchCustomerScreensWhenIdle`). Форма отзыва
  (`ReviewFormModal`, размер и цвет — `NeumorphicSelect`) — тоже окно из `lazyWindows.ts`, но в простое не грузится (Base UI,
  ≈ 36 КБ gzip): только при наведении, фокусе или нажатии «Написать отзыв». Статический
  импорт вернёт их в главный бандл. Клиент Cloud Functions грузится только для серверного заказа (`placeOrderCallable`
  в `firebase.ts`), пакет `re2js` (регулярные выражения pipelines Firestore, магазину не нужны) заменён заглушкой
  `src/vendor/re2js-stub.ts` (`resolve.alias` в `vite.config.ts`). Ленивые экраны, окна и разделы админки — через `lazyWithRetry`
  (`src/utils/lazyWithRetry.ts`, задача владельца 11.10, п. 8): чанк, которого нет после публикации, загружается ещё раз, потом страница
  обновляется один раз за 30 с; не вышло — «Раздел не открылся» / «Экран не открылся» с «Повторить» (`SectionErrorBoundary`), а не белый
  сайт. Ошибки отрисовки пишет в журнал только боевая сборка (`reportRenderError`): dev-сервер AI Studio («версия local») журнал не засоряет. Главный чанк — 267 КБ gzip (этап 8, было 325).
- Админка — отдельный чанк: разделы и `AdminNav` в `ProfileAdminPanel` (`src/views/profile/`) подключены через `lazy`, id и типы разделов лежат
  в `adminSections.ts`. Компоненты админки (и `NeumorphicSelect`) не импортировать статически в код покупателя:
  Base UI и графики вернутся в главный бандл (раздельная загрузка сократила начальную с ~682 до ~386 КБ gzip).
  Библиотеки PDF (`html2canvas`, `jspdf`) тоже грузятся по требованию: в аналитике — `preloadPdfLibraries` при
  наведении, в этикетках — `import('jspdf')`; статический импорт вернул бы их в главный бандл. Скорость панели:
  - загрузчики разделов — `adminLoaders.ts` (только `import()`); администратору код панели подгружается заранее
    (`prefetchAllAdminWhenIdle` в простое, `prefetchAdmin` при наведении/нажатии на кнопку панели и на вкладки);
  - смена раздела — `startTransition`, один `Suspense` над разделами: текущий раздел остается на экране, пока грузится
    следующий (у вкладки — спиннер), «Загрузка раздела…» только при первом открытии;
  - график аналитики (recharts) — отдельный чанк `AdminAnalyticsChart`, карточки показываются без него;
  - тяжелые списки (заказы, клиенты) — по 20 карточек с «Показать ещё» (`usePagedList`, `AdminShowMore`); поиск и фильтры —
    по всему списку, новый запрос начинает с первых 20 (`docs/orders-scale-plan.md`, этап 1).
- Несохраненное — `src/utils/unsavedChanges.ts`:
  - форма сообщает о правках через `useUnsavedChanges(dirty, 'Название')`;
  - `dirty` форм со снимком при открытии считает `useChangedSince(key, [поля])`;
  - при закрытии панели (×, клик по фону, Escape) и при смене раздела панель спрашивает «Закрыть/Перейти без
    сохранения?»; при уходе со страницы спрашивает браузер.

  Окно-форма закрывается через `useDiscardGuard` и `DiscardChangesDialog`, это касается и Escape. «Витрина»
  применяется кнопкой «Применить» (липкая панель при изменениях). Обновление из базы не затирает неприменённые правки.
- Сохранение: списки админки сохраняются через `syncAll*` (только запись, частями по 450 — лимит батча 500), в них
  передаются только изменённые элементы (`changedItems(prev, next)`: админка заменяет объект, а не мутирует его),
  удалённое убирает `deleteRemovedDocs`. Товары и заказы пишутся только изменёнными полями (`update`, `changedFields`
  из `src/utils/fieldChanges.ts`, аудит админки 09.10, находки 6 и 7): массовое действие не возвращает остаток, списанный
  заказом в те же секунды. Промокоды — тоже изменёнными полями и без `usedCount`/`lastOrderId` (их пишет заказ покупателя,
  аудит 29.10, находка 10). Форма товара кладёт на товар из базы только изменённое в ней (`mergeFormIntoLive`, находка 9),
  «Корректировка заказа» меняет склад только после сохранения заказа (находка 1). Правка заказа в полях покупателя (статус, оплата, отмена — `BUYER_ORDER_FIELDS`) пишется,
  только пока в базе то состояние, что видел владелец; иначе ничего не пишется, тост «изменил покупатель» и `false`. Записи из админки (`src/app/useAdminActions.ts`) — через `persist(label, ...writes)` из `useToasts`: при ошибке
  тост «Не сохранено: …» и `false`; «Сохранено» показывать только после ответа базы (`AdminListEditor`, «Витрина»,
  «Промокоды» ждут `Promise<boolean>` от `onSave`/`onUpdateSettings`/`onUpdatePromos`). Тосты-ошибки не исчезают сами. Записи покупателя, которые
  нельзя терять молча (профиль, очистка чата), — тоже через `persist`; профиль — `onUpdateProfile` → `Promise<boolean>`
  (`useProfile`): формы профиля, адреса, мерок и «Подбор размера» закрываются и пишут «Сохранено» после `true`, при отказе
  остаются с введённым, а профиль на экране возвращается; счётчик промокода после заказа — в консоль
  с номером заказа (заказ уже оформлен).
- Подсказка «для чего это» — только `AdminHint` (`src/components/admin/AdminHint.tsx`, тексты — `docs/admin-wholesale/hints.md`):
  рядом с подписью поля или кнопкой, не внутри `<button>`, `<label>`, `<a>` и заголовка (вложенная кнопка — неверная разметка,
  заголовок прочитался бы с «Что это: …»). Повторяющейся строке — у первой строки или в шапке списка. Имя кнопки «Что это: {подпись}»
  содержит подпись, поэтому сценарий e2e ищет саму кнопку с `exact: true`.
- «Товары»: действия с отмеченными товарами — панель внизу списка (`ProductSelectionBar`: «Выбрано: n», «Снять с продажи»,
  «В продажу», «Ещё» → окно массовых операций на нужной вкладке, `initialTab`); окно массовых операций закрывается и снимает
  выбор после ответа базы и показывает товары, у которых цена станет ниже закупки (`belowCostLines`). Цена и «Остаток» в строке
  открывают быструю правку (`ProductQuickPriceDialog`, `ProductQuickStockDialog`, расчёт — `src/utils/quickProductEdit.ts`):
  остаток — по вариантам через `applyAdminStockChanges` на разницу с остатком при открытии окна (продажа за это время не теряется) (этап 4 `docs/admin-wholesale-plan.md`).
- Строка списка: 2–3 частых действия на виду, редкие — в меню «Ещё» (`AdminActionMenu`, Base UI Menu, портал поверх
  панели), удаление — последним пунктом после черты и через подтверждение. Выбор одного значения из кнопки (статус заказа и оплаты
  в «Заказах») — `AdminChoiceMenu` (Base UI Menu, `menuitemradio`): Escape закрывает только меню, а не панель. «Заказы»: чипы статуса (`role="radio"`,
  отмененные — отдельным чипом; подписи — `ORDER_STEP_LABELS`, оплата — `PAYMENT_STATUS_LABELS`), чип «Ждут проверки чека N»
  (`aria-pressed`, фильтр оплаты `receipt_review`) и «Фильтры (n)» (период, оплата, доставка и способ оплаты — названия из самих
  заказов, не из кода). Карточка заказа свёрнута (этап 5 `docs/admin-wholesale-plan.md`): номер, клиент, сумма, статусы,
  предупреждения и одно главное действие — следующий шаг цепочки (`orderMainAction`: «Дальше: …», «Добавить трек», «Забрать
  заказ»); товары, адрес и история — под «Подробнее», чат, печать и правка состава — в «Ещё».
- На телефоне (< sm) панель администратора во весь экран; в чате поддержки карточка заказа свернута. Вход в панель —
  наверху профиля. Форма товара — блоки на одной странице (`ProductFormBlock`, этап 4 `docs/admin-wholesale-plan.md`):
  «Основное → Цены → Фото → Варианты и остатки → Описание и характеристики»; новый товар открывает все, знакомый —
  «Основное» и «Цены», закрытый блок показывает, что в нём заполнено, и не рисует поля (состояние формы — только
  в `useProductForm`); ошибка проверки открывает все блоки. «Цены» (`ProductFormPrices`): под закупкой в $/¥ —
  «По курсу: … ₽» и «Подставить» тем же `repriceProduct`, что «Применить», новый товар берёт цену по курсу, пока своей
  цены нет; цена ниже закупки — предупреждение, не запрет. «Отмена / Создать» закреплены внизу окна. Проверка формы
  товара — одна, на «Сохранить»: список ошибок над этими кнопками (`role="alert"`, дальше обновляется сам), без тостов; Enter в поле не отправляет
  форму, а в строке «добавить» (ссылка на фото, цвет, размер — `data-enter-adds`) нажимает её кнопку. Счётчик «Место под
  фото и описание» (`src/utils/productSize.ts`, запас до 1 МиБ) считает фото превью (полные — в `product_photos`, превью
  при записи уходят в `product_previews`), товар
  больше запаса не сохраняется. Форма закрывается и пишет «сохранен» только после ответа базы (`onUpdateProducts` →
  `Promise<boolean>`). Категория не подставляется: у нового товара пусто и «Выберите категорию» в списке ошибок, а артикулы
  вариантов, добавленных до выбора («WS-PR…»), перестраивает под выбранную `recategorizeSkuCode`; фото
  в галерею добавляется без тоста, ошибка загрузки — в том же списке (аудит UX 03.10, находки 16, 17). Форма промокода —
  так же: одна проверка со списком над кнопками, код не повторяет код другого промокода без учёта регистра и при правке,
  форма закрывается только после ответа базы (находка 5). Поля ввода текста в админке — `resize-y`, как в FAQ.
- «Промокоды» (этап 8 `docs/admin-wholesale-plan.md`, часть 2): список, форма (`promos/PromoForm.tsx`) и «Пачка кодов»
  (`promos/PromoBatchGenerator.tsx`) — отдельные экраны; поиск, чипы статуса и пачка одной строкой — только
  `src/utils/promoList.ts` (пачка — коды с id `batch-{время}-{n}`). Лимит использований по умолчанию пустой: код с лимитом
  применит только вошедший через Google (`promoSignInProblem`), об этом говорят поле и карточка кода.
