# Скиллы Claude Code в этом репозитории

Скиллы лежат в `.claude/skills/` и подгружаются в каждую сессию Claude Code с этим репозиторием, в том числе в облачную:
заранее Claude видит только название и описание скилла, а сам текст читает, когда задача подходит под описание.
Постоянные правила остаются в `CLAUDE.md`; скилл хранит порядок шагов повторяющейся работы и то, чего в `CLAUDE.md` нет.

| Скилл | Когда срабатывает | Что даёт сверх `CLAUDE.md` |
|---|---|---|
| `shipping-prs` | работа готова к PR, «доведи до зелёного», «слей, если зелёный», красный CI, отказ слияния 405 | скрипт `checks.sh` выбирает проверки CI по изменённым файлам; порядок «свежий `main` → снова зелёный → squash с `expectedHeadSha`»; проверка публикации после слияния |
| `doing-plan-stages` | «сделай этап N», «следующий этап», план из `docs/` | зависимости и решения владельца до начала, замер визита до и после, что и где отметить в плане |
| `changing-firestore-data` | новое поле или коллекция, `firestore.rules`, permission-denied | чек-лист из разбросанных мест: правило, тесты, старые документы, выпуск двумя PR, копия базы, индекс каталога |
| `writing-e2e-scenarios` | новый или красный сценарий в браузере, «добавь e2e» | как устроены проекты и данные сценариев, запуск одного файла за 20 с, как искать причину падения через раз |
| `prompt-brief` | проверить или собрать запрос для Claude | был раньше как `claude-brief`: слово «claude» в имени запрещено, поэтому переименован, команда теперь `/prompt-brief` |
| `graph-pilot` | вопросы о коде по графу Graphify, «покажи граф на телефоне» | сторонний скилл (#150): одна команда graphify на вопрос, запрет платных и сетевых команд, `phone_view.py` — кусок графа для телефона |
| `finding-skills` | скилл или команда ECC не из списка, «какие есть скиллы для…», «подбери скилл», «Unknown skill» | каталог ≈ 350 скиллов и команд ECC с описаниями (`catalog.md`, пишет `ecc-skill-fixes.py`): как найти, показать владельцу и выполнить скилл из каталога |

## Откуда правила

Только официальные материалы Anthropic. Пересказ `anthropic-skills-guide.md`, который прислал владелец, сверен с ними;
где он расходится с оригиналом, сделано по оригиналу (раздел «Расхождения» ниже).

- [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) — «Практики»
- [Claude Code: Skills](https://code.claude.com/docs/en/skills) — «Claude Code»
- [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5) — «Opus 5.5»
- [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) — «Промптинг»

| Правило | Как применено | Источник |
|---|---|---|
| `name` — строчные буквы, цифры, дефисы, до 64 знаков, без «claude» и «anthropic»; лучше форма на -ing | `shipping-prs`, `doing-plan-stages`, `changing-firestore-data`, `writing-e2e-scenarios` | Практики: Skill structure, Naming conventions |
| `description` — что делает и когда применять, от третьего лица, до 1 024 знаков, с ключевыми словами | «Доводит… Используй, когда…» со словами, которыми просит владелец, и текстами ошибок | Практики: Writing effective descriptions |
| Главный сценарий — в начале описания: `description` с `when_to_use` обрезается на 1 536 знаках | 359–412 знаков, главное — первой фразой | Claude Code |
| Только то, чего Claude не знает; SKILL.md до 500 строк | 51–98 строк; правила из `CLAUDE.md` не пересказаны, а названы | Практики: Concise is key, Token budgets |
| Свобода — по хрупкости: хрупкое — точная команда без смены флагов, остальное — общие указания | слияние и проверки — точные команды и скрипт; как писать сценарий — указания и образец | Практики: Set appropriate degrees of freedom |
| Многошаговая работа — чек-лист, который Claude копирует и отмечает; петля «проверил → исправил → снова» | чек-листы в трёх скиллах; `checks.sh` и `test:rules` до зелёного | Практики: Use workflows for complex tasks, Implement feedback loops |
| Готовый скрипт вместо генерируемого кода; скрипт выполняется, а не читается; ошибки обрабатывает сам | `checks.sh` сам ставит пакеты, проверяет Java и пишет, какая проверка упала | Практики: Provide utility scripts, Solve, don't defer |
| Файл скилла в команде — через `${CLAUDE_SKILL_DIR}` | `bash "${CLAUDE_SKILL_DIR}/checks.sh"` | Claude Code: String substitutions |
| Ссылки — на один уровень от SKILL.md | у скиллов нет вложенных файлов, кроме скрипта | Практики: Avoid deeply nested references |
| Инструменты MCP — полным именем `Сервер:инструмент` | `github:merge_pull_request`, `github:get_job_logs` | Практики: MCP tool references |
| Конкретные примеры; один способ по умолчанию, а не список вариантов | заголовки коммитов из истории `main`, образец сценария; одна команда на шаг | Практики: Examples pattern, Avoid offering too many options |
| Одно понятие — один термин | «проверки», «сценарий», «этап» — везде одинаково | Практики: Use consistent terminology |
| Причина вместо запрета и без «КРИТИЧНО / ОБЯЗАТЕЛЬНО» | у каждого ограничения — «потому что…» | Промптинг: Add context to improve performance; Tool usage (dial back aggressive language) |
| Вся задача, что значит «готово» и где остановиться; задача — чек-листом | в конце скиллов — «Готово — это…», остановки названы (слияние без разрешения, нет решения владельца) | Opus 5.5: Unattended agentic runs |
| Необратимое — с подтверждением | слияние — только по разрешению владельца, боевая база — только владелец | Промптинг: Balancing autonomy and safety |
| Не подгонять под тесты | сценарий не отключать и не ретраить, тест правила не ослаблять | Промптинг: Avoid focusing on passing tests and hardcoding |
| Три проверочных сценария; проверка на всех своих моделях; Claude A пишет, свежий Claude B проверяет | ниже, раздел «Проверка» | Практики: Build evaluations first, Test with all models you plan to use, Develop Skills iteratively with Claude |

## Расхождения пересказа с оригиналом

- Оглавление длинного файла: пересказ и его скрипт требуют заголовок «Содержание», оригинал — оглавление в начале файла
  без требований к форме. Поэтому замечание скрипта к `prompt-brief/правила.md` (оглавление было строкой) по оригиналу не
  нарушение; строка всё равно стала заголовком, чтобы замер был чистым.
- Форму имени на -ing пересказ не упоминает, оригинал советует; новые скиллы названы так.
- Пересказ советует проверять «лучше на Haiku», оригинал — на всех моделях, которыми пользуетесь: скиллы проверены
  на Haiku и Opus.

- **ECC 2.2.3** (`~/.claude/plugins/cache/ecc/ecc/2.2.3/skills/`, 293 скилла): до правки 120 нарушений у 61 скилла — 42 файла

  `ecc-install.sh` после установки запускает `.claude/hooks/ecc-skill-fixes.py` — только правки формы, которые руководство
  разрешает без решения владельца: крупные разделы длинного SKILL.md дословно в `reference/<раздел>.md` (на месте раздела —

## Список скиллов, который видит Claude

Claude выбирает скилл по описанию из списка, а список ограничен ~1 % окна (`skillListingBudgetFraction`; в облачной сессии —
≈ 30 000 знаков, ≈ 9 800 токенов). Встроенные скиллы Claude Code получают описание всегда, остальные — по частоте
использования (`skillUsage` в настройках контейнера), а облачный контейнер каждый раз новый: у всех ноль, и описания доставались
первым по порядку. 06.10 из 414 записей описание было у 98: у 78 команд ECC (многие — для чужих стеков) и ни у одного из
15 скиллов Anthropic (`docx`, `pdf`, `xlsx`…) — их Claude сам не вызывал.

Бюджет в коде Claude Code (`bVt`): окно модели × 3 знака × 0,01 — у Opus 5.5 и Sonnet 5.5 с окном 1M это 30 000 знаков,
у Haiku (200K) — 8 000, и описания проекта и ECC у него обрезаются (поэтому проверять список — только на окне 1M).

`skillOverrides` в `.claude/settings.json` для скиллов плагинов не действует: Claude Code для них сразу отвечает «on» и смотрит
только файлы скилла (проверено в коде и в `/context` свежего процесса). Поэтому решения владельца сделаны в `ecc-skill-fixes.py`:

- 06.10 («ECC: только ~30 нужных») — в списке только скиллы и команды ECC из `.claude/ecc-visible.txt`, весь перечень
  укладывается в бюджет целиком, у всех описание, порядок не важен;
- 07.10 («остальные — с описанием, Claude подбирает по запросу») — остальные не помечаются «только ручной вызов», а уходят
  в каталог: `SKILL.md` → `SKILL.md.catalog`, `имя.md` → `имя.md.catalog` (Claude Code их не грузит, относительные ссылки
  внутри скилла целы). Правка пишет `.claude/skills/finding-skills/catalog.md` — имя, вид и описание автора по разделам
  (фронтенд первым, чужие стеки и области в конце); скилл `finding-skills` ищет в нём по словам задачи, показывает
  владельцу или сразу читает файл и выполняет его. Пометка «только ручной вызов» 06.10 ломала просьбу словами: на
  `disable-model-invocation` Claude Code отвечает «Ask the user to run /ecc:имя… Do not replicate this skill's workflow by
  other means». Две команды, которые автор ECC сам сделал ручными (`auto-update`, `setup-pm`), остаются на месте и в каталоге
  помечены. Вызов `/ecc:имя` у скиллов из каталога больше не работает — просить словами.

Чтение папки плагина разрешает `ecc-install.sh` правилом `Read(//root/.claude/plugins/cache/ecc/**)` в `~/.claude/settings.json`:
без него сессия спрашивает разрешение на каждый файл скилла из каталога. То же правило в `.claude/settings.json` проекта
Claude Code не применяет — `~/.claude` у него в списке чувствительных папок (как `.bashrc`, `.gitconfig`), и открыть её могут
только настройки пользователя; запись `~/…` в правиле тоже не сработала. Правило, которое хук пишет при старте, действует уже
в первом процессе (проверено: файл в пустом контейнере, чтение без запроса). Подключать плагин рабочей папкой
(`additionalDirectories`) не стали: в нём `.claude/rules` и `CLAUDE.md` для разработки самого ECC.

по каталогу, три скилла с пояснением по-русски; «используй скилл ecc:motion-patterns…» — «Unknown skill», затем
`finding-skills`, каталог и файл скилла. Добавляя имя в `.claude/ecc-visible.txt`, проверь, что все записи по-прежнему
с описанием: перечень сверх бюджета снова отдаёт описания по порядку, и последним теряет его `xlsx`.

## Правила ECC

С 07.10 (решение владельца) правила ECC стоят так, как велит его README: плагин их распространять не может, поэтому
`rules/common` и пакеты стека магазина `typescript`, `react`, `web` копируются папками — второй способ README, в
`.claude/rules/ecc/` проекта (27 файлов). Первый способ, `~/.claude/rules/ecc/` хуком, в облаке не работает: Claude Code
читает память до хуков старта, перечитать её хук не может (в выводе SessionStart есть только `reloadSkills`), а контейнер
каждый раз новый — проверено свежим процессом: правила, положенные хуком, в `/context` не появились. `ecc-install.sh` сверяет
копию с плагином закреплённой версии и при новой версии ECC обновляет её — разница попадёт в PR.

`common` (10 файлов, ≈ 7 000 токенов) читается всегда; остальные — с полем `paths` и подгружаются, когда открыт файл
`.ts/.tsx/.js/.jsx`. Где правила расходятся с `CLAUDE.md`, верен `CLAUDE.md` (решение владельца 07.10): названия коммитов и PR —
по-русски, без `feat:`/`fix:` (в правилах — conventional commits), описание PR — по шаблону, порог покрытия 80 % и обязательный
TDD не требуются. `CLAUDE.md` и `.claude/` из репозитория ECC — для разработки самого ECC и не ставятся.
