Составлен 03–04.10.2026 по коду `main` 2516c1a. Задача владельца: если сайт сломается у покупателей или не опубликуется,
узнать об этом первым, а не от покупателей, и не потерять данные магазина.

Проверено: код сайта, workflow `deploy.yml`, `share-pages.yml`, `ci.yml`, правила Firestore, кнопки копии и
восстановления в админке. Не проверялось: настройки Firebase Console и уведомлений GitHub владельца (доступа нет), боевой
сайт из среды Claude (сеть закрыта) — проверка «сайт открывается» опробована на локальной сборке.

## Ждёт владельца

Шаги по одному, все бесплатные:

1. **Уведомления GitHub** (после этапа 1): github.com → аватар → Settings → Notifications → «Participating, @mentions and
   custom» — включить Email (и Push, если стоит приложение GitHub на телефоне). Тогда задача «Сбой сайта» придёт письмом
   и пушем. [Документация GitHub](https://docs.github.com/en/account-and-profile/managing-subscriptions-and-notifications-on-github/setting-up-notifications/configuring-notifications).
2. **Там же, раздел «Actions»** — «Only notify for failed workflows»: GitHub сам пишет о любом упавшем запуске, который
   вы начали (слияние PR = ваш запуск деплоя).
3. **Решение (этап 3, по желанию):** присылать ли раз в сутки письмо «на сайте N ошибок за день» без текста ошибок.
   Его считал бы workflow с ключом деплоя: по README у сервисного аккаунта роль Firebase Admin, которая, судя по
   описанию роли, даёт и чтение базы (не проверено). Без письма ошибки видны в админке («Аналитика» → «Ошибки на сайте»).
4. **После Blaze (направление 8):** Firebase Console → Firestore → «Disaster recovery» → ежедневные копии
   ([документация](https://firebase.google.com/docs/firestore/backups)).

## Выбор

| Что | Варианты | Выбрано и почему |
|---|---|---|
| Куда идут ошибки покупателей | А. В свою базу Firestore, владелец видит их в админке. Б. Sentry или похожий сервис (бесплатно до 5 000 ошибок в месяц). В. В GitHub | **А.** Б и В отправляют текст ошибок стороннему сервису, а в нём бывают почта или телефон покупателя (например, `handleFirestoreError` пишет почту вошедшего) — это решение владельца, а не кода. Своя база уже хранит данные покупателей и закрыта правилами. Цена: запись ≈ 1 документа на ошибку — в бесплатной квоте |
| Как не дать постороннему засорить журнал | Правило Firestore: только создание, только перечисленные поля с лимитом длины, id документа — «час_ячейка» с ячейкой 0–29 | Не больше 30 записей в час на весь сайт, что бы ни делал посторонний (≈ 720 в сутки, ≤ 2 МБ), читает и удаляет только администратор. Ограничить по покупателю нельзя: посетитель не входит в аккаунт, а анонимных входов посторонний может завести сколько угодно. Повторы одной ошибки за визит браузер не шлёт |
| Как владелец узнаёт о сбое публикации | А. Письмо GitHub о красном запуске (настройка владельца). Б. Задача в GitHub, назначенная владельцу | **Б и А.** Задача не теряется среди писем, закрывается сама, когда следующий запуск прошёл, и видна в приложении GitHub. Только ссылки и названия шагов, без данных базы |
| Сайт открывается | Проверка после каждой публикации (новая сборка на месте, в Chrome нет ошибок JS) и раз в 3 часа (главная и код приложения отвечают) | Раз в 3 часа хватает, чтобы узнать о лимите трафика в тот же день; проверка по расписанию не читает базу |
| Копии базы до Blaze | Ручная копия + напоминание по понедельникам (есть) | Ночная выгрузка в GitHub Actions отклонена планом `firestore-free-tier-plan.md`: персональные данные покупателей окажутся в GitHub |

## Этап 1. Оповещения о публикации — сделано, #129

- `alerts.yml`: когда публикация `main` (`deploy.yml`), обновление превью (`share-pages.yml`) или проверка сайта падает,
  открывается задача «Сбой сайта: …» с меткой «сбой сайта», назначенная владельцу: ссылка на запуск, коммит, шаг,
  который не прошёл. Повтор на том же коммите ничего не добавляет (превью обновляются каждый час — иначе письма
  каждый час), новый коммит с ошибкой — комментарий. Следующий успешный запуск закрывает задачу «Починилось».
- `scripts/site-check.ts`: главная отвечает 200 и это страница магазина, код приложения скачивается; с `--expect` —
  на сайте именно опубликованная сборка; с `--browser` — в Chrome на 390 px нет ошибок JS и экран не пустой.
- `deploy.yml`: шаг «Сайт открывается после публикации» (`--expect --browser`); `site-check.yml`: раз в 3 часа
  без браузера и без чтения базы.

## Этап 2. Ошибки покупателей — сделано, #133

- `src/utils/errorReporter.ts`, запускается в `main.tsx` (не в `App.tsx`): необработанные ошибки и отклонённые промисы,
  экраны, которые не нарисовались (`onCaughtError`/`onUncaughtError` у `createRoot`), и `console.error` — в нём сайт
  пишет свои сбои («Order was not saved», «Stock … was not written off» и т. п.). Отчёт собирает `src/utils/clientErrors.ts`:
  почта и номера телефонов заменяются на «[почта]», «[телефон]»; из аргументов `console.error` берутся только строки
  и тексты ошибок (объект заказа в журнал не попадёт); адрес — только путь страницы. Шум (нет сети, закрытое окно
  Google, расширения браузера) не пишется. Одна ошибка за визит — один раз, не больше 5 за визит. Пишет только боевая
  сборка и проверочная (с пометкой «проверка» у версии).
- Коллекция `client_errors/{час}_{ячейка}`, правило `isClientErrorReport` и три теста в `tests/firestore.rules.test.mjs`:
  посетитель без входа пишет отчёт, ячейка не перезаписывается, 30-я ячейка и чужой час — нет, лишние и длинные поля —
  нет, время — только серверное; читает и удаляет только администратор. В резервную копию журнал не входит.
- «Аналитика» → «Ошибки на сайте» (`AdminSiteErrorsCard`, в чанке админки): за сутки и за 14 дней, одинаковые ошибки
  одной строкой — сколько раз, когда последний, страницы, устройство и браузер, версия сайта, «Подробности для
  разработчика»; «Очистить» через подтверждение. Записи старше 14 дней удаляются при открытии раздела.
- `AppErrorBoundary` в `main.tsx`: «Что-то пошло не так» с «Обновить страницу» вместо белого экрана; если кода экрана
  после новой публикации уже нет — «Сайт обновился… корзина и избранное сохранятся».
- Версия сборки в отчёте — `VITE_RELEASE` (первые 7 знаков коммита из `GITHUB_SHA`, `vite.config.ts`).
- Сценарии `tests/e2e/shop/site-errors.spec.ts` (390 и 1280 px): ошибка покупателя без почты видна в карточке;
  экран, которого нет после публикации, показывает «Сайт обновился», а не белую страницу.
- Главный чанк: +2,0 КБ gzip (270,9 → 273,0, замер 04.10).

Доработка 04.10: сценарий «Ошибки на сайте» изредка падал в CI — отчёт не появлялся в базе. Причина: при занятой
ячейке браузер пробовал ещё только одну, и отчёт пропадал, если обе были заняты (воспроизведено: 26 из 30 ячеек
заняты — старый код терял отчёт, новый нет). Теперь `send` перебирает ячейки часа в случайном порядке, пока не найдёт
свободную: отчёт теряется, только если заняты все 30. Сценарий ждёт запись до 20 с — запись ждёт соединения страницы
с базой, а при всех сценариях разом оно медленнее.

## Если что-то сломалось: порядок восстановления

**Сайт не открывается после публикации.** Firebase Console → Hosting → «Release history» → у прошлой версии «⋮» →
«Rollback» — покупатели сразу получают прошлую версию ([документация](https://firebase.google.com/docs/hosting/manage-hosting-resources)).
Правила Firestore откатываются отдельно: Console → Firestore → Rules → история → прошлая версия → «Publish». Потом —
Claude в проекте: «Разбери сбой сайта» и ссылка на задачу; исправление идёт обычным PR.

**Сайт не открывается без публикации.** Console → Hosting → Usage: если упёрлись в дневной лимит трафика бесплатного
тарифа, лимит обнуляется раз в сутки (по тихоокеанскому времени — утром по Москве), а на Blaze его нет.

**Данные испорчены или удалены.**
1. Ничего не исправлять руками, пока не сделана копия того, что есть сейчас: «Витрина» → «Скачать копию базы».
2. «Витрина» → «Восстановить из копии» → файл последней хорошей копии. Режим «Только недостающие» возвращает
   удалённое и не трогает изменённое после копии; «Как в копии» возвращает и изменённые документы к виду из копии.
   Ничего не удаляется.
3. Отзывы, голоса «Полезно» и список администраторов браузер не восстанавливает (их пишут только авторы или Console):
   если пропали они — Claude в проекте, с файлом копии.
4. После Blaze с ежедневными копиями: Console → Firestore → Disaster recovery → копия за нужный день → «Restore» в новую
   базу, затем перенос, как в `firestore-free-tier-plan.md`.
