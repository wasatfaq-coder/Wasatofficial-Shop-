# Промпты для роста магазина

Каждое направление начинается с плана в `docs/` и продолжается этапами по одному PR (см. [README](README.md)).
Если не решили, что делать первым, — промпт 0: из него получится дорожная карта, а к ней подойдут промпты 1–9.

В промптах есть то, что в коде уже известно об устройстве магазина. Если к моменту запуска что-то из этого
поменялось, Claude скажет об этом в «Найдено».

---

## 0. Куда расти: интервью и дорожная карта

```
Я хочу развивать Wasat Shop, но пока не решил, в каком порядке. Задавай мне вопросы по одному: сколько сейчас
товаров, заказов и посетителей и сколько я жду через [полгода]; кто, кроме меня, будет работать в админке; как
покупатели платят сейчас и как я хочу; откуда они приходят; что мешает больше всего. Начни с вопросов, от ответа на
которые сильнее всего меняется порядок работ, и к каждому дай 2–3 варианта ответа.

Когда вопросов не останется, проверь по коду, что из моих планов упрётся в нынешнее устройство: подписки на целые
коллекции в `src/utils/firebaseSync.ts`, фото внутри документов товаров, всё состояние в `src/App.tsx`, одна роль
администратора в `firestore.rules`, заказы в браузере при выключенном `serverOrdersEnabled`.

Готово — это PR с `docs/roadmap.md`: цели с цифрами, направления по порядку со ссылкой на промпт из
`docs/prompts/scaling.md` и оценкой в PR, риски и что нужно от меня (тариф, доступы, договоры). Код не меняй.
```

## 1. Больше товаров и посетителей

```
Я планирую [1 000] товаров и [1 000] посетителей в день. Сейчас каждый посетитель загружает весь каталог
с превью фото (≈ 45 КБ на фото в документе товара; полные фото — документы `product_photos`, этап 6 аудита 02.10;
Storage без тарифа Blaze недоступен). Покупателю нужно, чтобы каталог открывался быстро, а мне — чтобы счёт Firebase не рос
вместе с числом посетителей. С учётом этого: спроектируй и начни переход — фото в хранилище файлов с превью
нескольких размеров, каталог частями и по запросу вместо подписки на всю коллекцию, отзывы по товару, а не все сразу.

Готово — это план `docs/catalog-scale-plan.md` по шаблону `docs/templates/audit-plan.md` и первый PR из него.
Товары со старыми base64-фото должны показываться, пока миграция не пройдёт. Перенос боевых данных я запущу сам по
инструкции из плана: боевую базу из репозитория не восстановить.

Останавливайся и спрашивай, только если решение требует платного тарифа или меняет то, что видит покупатель.
```

## 2. Больше заказов

```
Заказов станет [30] в день. Сейчас по умолчанию заказ оформляет браузер покупателя и сам списывает остатки
(`completeOrderLocally` в `src/App.tsx`), серверный режим `placeOrder` выключен, а админка загружает все заказы
и всех покупателей сразу. Мне нужно, чтобы два покупателя не купили один последний товар, а «Заказы» и «Клиенты»
открывались быстро и через год. С учётом этого: подготовь переход на серверные заказы и постраничные списки
в админке.

Готово — это PR с `docs/orders-scale-plan.md`:
- что изменится для покупателя и для меня;
- пошаговая инструкция включения для меня: тариф Blaze, переменная `DEPLOY_FUNCTIONS`, флаг `serverOrdersEnabled`
  (README, «Как включить»);
- тест одновременных заказов последнего товара на эмуляторах;
- этапы по одному PR; первый — постраничные «Заказы» и «Клиенты».
```

## 3. Сотрудники в админке

```
Я хочу взять [менеджера по заказам / кладовщика / оператора чата]. Сейчас любой администратор (`ADMIN_EMAIL` или
`admins/{uid}`) может всё: цены, промокоды, реквизиты, документы, удаление. Мне нужно, чтобы сотрудник делал свою
работу, но не мог менять цены, реквизиты и чужие права. С учётом этого: спроектируй роли — [роль: что ей можно;
роль: что ей можно] — в `firestore.rules`, в админке и в Cloud Functions.

Готово — это PR с `docs/staff-roles-plan.md`: таблица «роль — разделы админки — что может менять», тесты правил на
каждую роль и этапы по одному PR. Права владельца не должны уменьшиться ни на одном этапе: иначе ошибку в ролях
будет некому исправить.

Останавливайся и спрашивай, если роли из моего списка нужен доступ, которого я не назвал.
```

## 4. Онлайн-оплата

```
Сейчас способы оплаты — только тексты из раздела «Оплата», денег сайт не принимает. Я хочу принимать оплату картой
и [СБП] через [платёжная система — или «предложи 2–3»]. Покупателю нужно оплатить за минуту, мне — видеть оплату
в заказе без ручной сверки. С учётом этого: спроектируй подключение — платёж создаётся на сервере, подтверждение
приходит уведомлением платёжной системы в Cloud Function, статус оплаты виден в заказе и в админке, есть возвраты
и чеки [уточни, кто формирует чеки по 54-ФЗ].

Готово — это PR с `docs/payments-plan.md`:
- сравнение провайдеров по комиссии, требованиям к продавцу и чекам — со ссылками на их документацию;
- схема «покупатель → сайт → платёжная система → функция → заказ»;
- что поменять в оферте;
- этапы по одному PR.

Ключи платёжной системы — только в секретах Cloud Functions: в коде или Firestore их увидит любой, кто откроет сайт.
Договор, выбор провайдера и ключи — за мной, вынеси их в «Ждёт меня».
```

## 5. Поиск и ссылки на товары

```
Покупатели должны находить товары в Яндексе и Google и видеть нормальное превью, когда я отправляю ссылку на товар
в мессенджере. Сейчас адреса экранов идут через `#` (`#/product/{id}`, `src/utils/navigation.ts`), а заголовок
и описание одни на весь сайт (`index.html`, в описании — «в стиле Neumorphism»). С учётом этого: оцени, что нужно,
чтобы страницы товаров индексировались и давали превью с фото и ценой, — адреса без `#`, заголовок и описание
у каждого товара, sitemap, разметка товара для поисковиков, превью для мессенджеров — и что из этого возможно на
Firebase Hosting без отдельного сервера.

Готово — это PR с `docs/seo-plan.md` (варианты, цена в работе и в деньгах, этапы) и первым этапом — тем, что не
меняет адреса: описание сайта для покупателей, превью, sitemap. Переход на адреса без `#` — отдельным этапом:
ссылки на товары, которые я уже разослал, должны продолжать работать.
```

## 6. Большая новая функция

```
Я хочу [функция — например, программа лояльности, подарочные сертификаты, онлайн-возвраты, уведомления о статусе
заказа в Telegram] для [кого]. Им нужно [что это даст]. С учётом этого: сначала задавай мне вопросы по одному обо
всём, что в задаче неоднозначно, начиная с тех, от ответа на которые сильнее всего меняется результат. Потом найди
по коду, что функция затронет: данные и `firestore.rules`, расчёт суммы в `src/shared/` и `placeOrder`, админку,
оформление, оферту.

Готово — это PR со спецификацией `docs/[функция]-spec.md` по шаблону `docs/templates/feature-spec.md` и этапами по
одному PR, без кода. Код — после того как я прочитаю спецификацию, промптом «Сделай этап 1 из …».
```

## 7. Код, готовый к росту

```
Чтобы новые функции делались быстрее и реже ломали старые, разнеси состояние и обработчики из `src/App.tsx` по
модулям экранов и данных — по карте из `docs/code-health-plan.md` (если её ещё нет, сначала составь её промптом 6
из `docs/prompts/audit.md`).

Готово — это серия PR, каждый переносит одну часть и не меняет поведения: проверки из «Когда готово» в CLAUDE.md
проходят, сценарии [оформление заказа, чат, сохранение товара в админке] на эмуляторах работают как раньше на 390
и 1280 px, а в описании PR сказано, что перенесено и как проверено. Ключи `manstyle_*`, экспорт
`src/utils/firebaseSync.ts` и адреса экранов оставь прежними: от них зависят данные покупателей и разосланные ссылки.

Останавливайся, если перенос требует изменить поведение: такое решение за мной.
```

## 8. Постоянная страховка: сценарии в CI

```
Прошлые PR проверялись сценариями Playwright на эмуляторах, но сценарии не сохранены, и следующая правка может
незаметно сломать оформление заказа. Мне нужно, чтобы главные пути проверялись в каждом PR сами. С учётом этого:
добавь в репозиторий сценарии на эмуляторах — [найти товар и оформить заказ с курьером; заказ в 1 клик; сообщение
в чат; вход администратора, смена цены и печать этикетки] — на 390 и 1280 px и шаг в CI.

Готово — это PR, где сценарии проходят локально и в CI, а в README написано, как их запустить. Тестовые данные
создаёт скрипт в эмуляторе: боевую базу тесты не трогают, её из репозитория не восстановить.
```

## 9. Резервные копии и оповещения

```
Если база повредится или сайт начнёт падать у покупателей, я сейчас узнаю об этом последним и, возможно, не смогу
вернуть данные: в репозитории ничего нет про резервные копии Firestore, а ошибки у покупателей пишутся только
в консоль браузера. С учётом этого: предложи [бесплатный / недорогой] способ — ежедневные копии Firestore,
оповещения об ошибках у покупателей и о неудачном деплое — и порядок восстановления из копии.

Готово — это PR с `docs/ops-plan.md`: пошаговая инструкция для меня, что включить в Firebase Console и Google Cloud
(со ссылками на документацию), что добавить в код одним PR и сколько это стоит в месяц. Настройки в консоли —
в «Ждёт меня», их делаю я.
```
