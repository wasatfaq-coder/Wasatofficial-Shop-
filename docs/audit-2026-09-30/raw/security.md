# Обзор рисков: безопасность и доступ (main a163f0c, 30.09.2026)

Тест атак: `scratchpad/risk/security/attacks.test.mjs` (копия правил там же, свой `firebase.json`, порты 8180/9160/4410/4510, проект `demo-audit-sec`). Результат: **13 из 13 прошли** (`# pass 13 # fail 0`, лог `attacks.log`). Шесть сценариев A — атаки при клиентских заказах, S1 — что в серверном режиме те же атаки отклоняются, B — атаки в обоих режимах, C1 — что защита держит.

**Коротко на вопросы владельца:**
- **Прочитать чужие заказы, адреса, телефоны, переписку** — нельзя: ни без входа, ни анонимному гостю, ни другому покупателю (C1).
- **Стать администратором** — нельзя: чужая почта владельца без подтверждения и запись в `admins/*` отклоняются (C1).
- **Изменить бонусы** — нельзя (C1).
- **Изменить статус уже созданного заказа** — нельзя.
- **Остатки, «Снят с витрины», счётчики промокодов, «оплаченные» заказы по любой цене** — при клиентских заказах **может любой посетитель без входа**. При серверных заказах эти лазейки закрыты (S1).
- **Без защиты в обоих режимах:**
  - все промокоды видны целиком;
  - чат и «Полезно» можно заспамить;
  - «Оплачен» ставится без оплаты.
- **XSS** не найден:
  - `dangerouslySetInnerHTML` в коде нет;
  - отчёт PDF экранирует поля (`esc`);
  - текст оферты выводится как текст;
  - CSV защищён от формул (`csvCell`).

## Проверить в консоли
- **Authentication → Sign-in method.** Какие провайдеры включены. Правила считают «покупателем» любого не-анонимного (`isCustomer`). Если включены Email/Password или Phone, фейковых покупателей для отзывов и «Полезно» можно создавать скриптом. Нужны только Google и Anonymous. Ещё там: защита от массовых регистраций, настройка «один аккаунт на email».
- **App Check.** В `firebase-applet-config.json` `recaptchaSiteKey` пуст, в коде App Check нет. Включить для Firestore, Functions и Auth — главный рычаг против спама (№ 5, 7, 8).
- **Firestore → Rules.** Совпадают ли опубликованные правила с `main` (см. «Не подтверждено» № 1). Есть ли в проекте база `(default)` или другие базы с правилами test mode: проект создан AI Studio (`ai-studio-applet-…`).
- **Firestore → документ `settings/server`.** Какой сейчас режим заказов. От него зависит, P0 ли находки № 1–3.
- **Storage.** `storageBucket` задан, а `storage.rules` в репозитории нет. Проверить, что правила Storage не открыты на запись.
- **Google Cloud → APIs & Services → Credentials.** Ограничения API-ключа `AIzaSyB3…`: HTTP-referrer — домены магазина; список API — только Firebase. Особенно убедиться, что ключом нельзя вызвать Generative Language (Gemini) API за счёт владельца.
- **IAM.** Роли сервисного аккаунта из `FIREBASE_SERVICE_ACCOUNT`: нужны Firebase Hosting Admin, Firebase Rules Admin, Cloud Functions Developer и Service Account User. Не Owner и не Editor. Сколько у него ключей и какого они возраста.
- **GitHub → Settings.** Environment `production`: есть ли правила защиты. Actions → Workflow permissions: read-only по умолчанию. Защита ветки `main`. Кто соавторы.
- **Google-аккаунт владельца** (`ADMIN_EMAIL` — единственный ключ ко всей админке, почта видна в коде сайта): включена ли двухэтапная аутентификация. Кто есть в `admins/*`.
- **Billing.** Бюджет и оповещения о расходах: спам из № 7–8 бьёт по счёту.

## Попутно
- **Чат (UX и данные):** админка загружает чат как `limit(500)` без сортировки (`firebaseSync.ts:712`). Когда в базе станет больше 500 сообщений, **новые обращения покупателей перестанут появляться в админке** — P1 для работы поддержки, даже без атаки.
- **Firestore (стоимость):** каждый посетитель подписан на целые коллекции `reviews`, `review_votes`, `promos` (`App.tsx:422-425`), а товар 521 КБ с base64-фото скачивается каждым — проверяющему стоимости.
- **Заказы:** клиентский режим берёт `totalPrice` из данных корзины (`App.tsx:1327`) и пишет заказ до списания склада без транзакции — проверяющему «Денег».
