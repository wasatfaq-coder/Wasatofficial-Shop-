# Полный UI/UX-аудит экранов скиллами ECC: аудит и план работ

План составлен 08.10 по решению владельца: проверить все экраны покупателя и админки на функциональные недочёты
и на соответствие стилю магазина. Аудит ещё не проводился — находки появятся по этапам, ниже.

Как проверяем: сборка с `VITE_USE_EMULATORS=true`, эмуляторы Firebase и данные сценариев (`tests/e2e/store.ts`; для админки
с нагрузкой — `tests/visit/orders1800.ts`), телефон 390 px (и 320) и компьютер 1280 px. Браузер — Playwright MCP
(`mcp__playwright__*`, Chromium из `/opt/pw-browsers`). В боевую базу аудит не пишет.
Не проверяется: настоящие фото и данные магазина (только данные сценариев), Safari и iOS (в облаке только Chromium),
настройки Firebase Console.

## Чем проверяем

Скиллы ECC стиля магазина не знают — эталон для них задаётся явно (см. «Эталон стиля»). Модели — по `.claude/rules/models.md`.

| Что ищем | Скилл или агент ECC | Модель | Что даёт |
|---|---|---|---|
| Кнопка работает по отдельности, но итог неверный (состояние, запись в базу, экран после действия) | `ecc:click-path-audit` | Opus 5.5 | Цепочка «нажатие → состояние → запись → экран» для каждой кнопки экрана |
| Сбой в браузере: ошибки консоли, формы, вход, раскладка на трёх ширинах | `ecc:browser-qa` | Sonnet 5.5 | Скриншоты 390 / 1280, ошибки консоли, итог «можно / нельзя» |
| Отступы, заголовки, кнопки, тени, цвета не по эталону | `ecc:design-system` (режим аудита), `ecc:make-interfaces-feel-better` | Sonnet 5.5 | Оценка по 10 параметрам и список расхождений с эталоном |
| Доступность WCAG 2.2 AA: подписи, фокус, контраст, зоны нажатия | `ecc:accessibility`, агент `ecc:a11y-architect` | Opus 5.5 | Находки с критерием WCAG |
| Живой сценарий целиком глазами покупателя | агент `ecc:gan-evaluator` | Sonnet 5.5 | Оценка сценария и замечания |
| Ревью правок по находкам | агент `ecc:code-reviewer` | Opus 5.5 | Как после любой правки кода (`CLAUDE.md`) |

## Эталон стиля

Находка «не по стилю» — только расхождение с этим списком (из `CLAUDE.md`, раздел «Интерфейс», и решений в
`docs/ui-audit-plan.md`). Совет ECC, который этому противоречит (например, убрать неоморфизм целиком или добавить
кремовый фон), — не находка, а пункт в «Не подтверждено» с причиной.

- Неоморфные классы `neu-*` из `src/index.css`, тени — только переменные `--neu-*`; рядом с `neu-*` нет `shadow-*`, `bg-*`,
  `active:scale-*`. Плоский вид допустим, если неоморфный не проходит WCAG AA (причина — в PR).
- Одна `neu-button-accent` на экран; удаление — `neu-button-danger` и `ConfirmDialog`; выпуклое — только то, что нажимается.
- Выбранное вдавлено (`neu-pill-active`), неактивное — плоское `neu-button-disabled`.
- Цвета — токены `@theme` (`accent`, `accent-strong`, графит для главной кнопки, `gold` — только бейджи «Хит/Premium»);
  статусы — `success/warning/danger` и `*-soft`; хексов акцента в классах нет.
- Шрифты: заголовки и `font-display` — Manrope 700/800; текст не мельче `text-[11px]`, абзацы от `text-xs`.
- Зона нажатия от 24 px, у частых действий покупателя — от 32 px; у кнопки-иконки — `aria-label`.
- Окна — `useDialogA11y`, выпадающие списки — `NeumorphicSelect`, переключатели — `NeumorphicSwitch`.
- Телефон — основной экран; компьютер (`lg:`) — шапка `DesktopHeader`, две колонки у товара, корзины и оформления.
- Покупатель не видит выдуманных данных: пустое — «не настроено» (`NotConfigured`).
- Дизайн без кремового и почти белого фона, курсива в заголовках, нумерации разделов 01/02/03, моноширинных подписей
  и кнопок-таблеток (предпочтение владельца).

## Как проходит этап аудита

1. Эмуляторы и сборка с `VITE_USE_EMULATORS=true`, данные сценариев; вход — `window.e2eSignIn`.
2. На каждом экране группы, 390 и 1280 px: `ecc:browser-qa` (консоль, скриншоты), `ecc:click-path-audit` (каждая кнопка
   до записи в базу и итогового экрана), `ecc:design-system` и `ecc:make-interfaces-feel-better` против «Эталона стиля»,
   `ecc:accessibility`.
3. Каждую находку второй агент пытается опровергнуть по коду и решениям владельца (как в аудите 07.10): подтверждённая —
   в «Находки» с доказательством (скриншот, строка кода, шаги), неподтверждённая — в «Не подтверждено».
4. Находка, уже записанная в другом плане `docs/`, не дублируется — ссылка на него.
5. Итог этапа — PR с обновлённым планом; P0 — сразу отдельным PR с тестом.
